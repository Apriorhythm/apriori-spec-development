# Requirement — cli-strictness (v2)

change: cli-strictness
target lineage: **v3 branch** (never merge to main or v2). Ships in the next minor (expected **3.3.0**) — it changes ERROR-path behavior only (what was silently ignored now fails loudly), which is the fail-closed direction; success-path behavior of every documented invocation is unchanged.

> v2 handling notes (P2): SREQ-1 → §Flag table declares every subcommand's surface. SREQ-2+SREQ-3 → `multi` now stops at ANY `-`-prefixed token (declared micro-change: a value literally starting with `-` was never expressible in docs), and an empty multi set is exit 2 naming the flag. SREQ-4 → repeat semantics declared (value=last-wins, multi=accumulates, flag=idempotent) with tests. SREQ-5 → S9-S12 added. SREQ-6 → current-state corrections: `new` today IGNORES extra positionals (arity enforcement is a declared change); `stamp` is already strict on count and today treats `--foo` as its positional (henceforth: unknown flag, exit 2 — declared change).

## Background — the problem (current state A)

Every subcommand parses argv with an ad-hoc loop that silently ignores anything it doesn't recognize. Consequences, all real today: `apriori verify --sepcs x` (typo) silently falls back to the config test-cmd and can verify the WRONG spec set while exiting green — fail-open in the one place the toolchain promises fail-closed; `apriori gate --hcange x` runs an unusable evaluation; no subcommand answers `--help` (users get usage only by triggering an error, exit 2). The top-level dispatcher handles `apriori --help`/`-h`/bare (usage, exit 0) and unknown SUBCOMMANDS (exit 2) correctly — the gap is inside the subcommands. Current strictness islands: `doctor` rejects stray positionals; `stamp` enforces exactly one argv entry (but counts `--foo` as that entry). `new` takes the FIRST non-flag token and ignores extras — `apriori new a b` silently uses `a` today.

## Goal (target state B)

One shared argv-parsing helper; every subcommand gets three uniform behaviors:

1. **`--help` (and `-h`) → that subcommand's usage on stdout, exit 0** — checked before any other validation, works even where required args are missing.
2. **Unknown `--flag` (or `-x`) → stderr `unknown flag '<flag>' for 'apriori <sub>'` + that usage, exit 2.** Nothing silently ignored anymore.
3. **Positional arity enforced**: `new` and `stamp` take exactly one positional; extras → exit 2 naming the first extra (a DECLARED change for `new`, which today silently ignores them); every other subcommand takes zero — a stray positional → exit 2 (doctor's rule generalized). For `stamp`, `--foo` stops being a legal positional and becomes an unknown-flag error (declared change).

## The helper (concrete contract)

`parseStrict(argv, spec)` where `spec = { sub: '<name>', usage: '<text>', flags: { '--name': 'value' | 'multi' | 'flag' }, positionals: 0 | 1, aliases?: {'-y': '--yes'} }` →
`{ ok: true, flags: {...}, positionals: [...] }` or `{ ok: false, code: 0|2, message }` (code 0 = help requested; the caller prints usage to stdout and returns 0; code 2 = the caller prints message + usage to stderr and returns 2).
- `'value'` consumes exactly the next token (missing value → exit 2 naming the flag; repeats: last-write-wins); `'multi'` consumes tokens until the next `-`-prefixed token — note SINGLE dash: `-x` now terminates consumption and then fails as an unknown flag (micro-change from 3.2.0's `--`-only rule; a value literally starting with `-` was never documented or expressible) — an EMPTY consumed set → exit 2 naming the flag; repeats accumulate (`--specs a --specs b` = both); `'flag'` consumes nothing and is idempotent on repeat.
- `--help`/`-h` anywhere → `{ok:false, code:0}` immediately.
- The helper lives in one new file (`lib/args.js`), zero-dep, required by every cli().

## Acceptance criteria (testable)

- S1. For EVERY subcommand in {new, status, verify, archive, check, init, update, stamp, gate, doctor}: `apriori <sub> --help` prints usage containing `apriori <sub>` on stdout and exits 0 — a single loop-test over the full list.
- S2. For EVERY subcommand: `apriori <sub> --no-such-flag` exits 2 and stderr names `--no-such-flag` — same loop, and no subcommand performs its action (nothing written; verify/doctor run no test command).
- S3. Stray positional on a zero-positional subcommand (e.g. `apriori status extra`, `apriori verify extra`) → exit 2 naming `extra`; `new`/`stamp` keep their exactly-one rule (zero or two → exit 2).
- S4. A `'value'` flag at end of argv with no value (`apriori verify --test-cmd`) → exit 2 naming the flag, never consuming `undefined`.
- S5. Success paths unchanged: the existing full test suite (142 tests) passes unmodified EXCEPT tests that themselves relied on silent-ignore or count-mismatch semantics — each such modification listed in the delta. `verify --specs a b c --test-cmd x` still consumes three spec targets.
- S6. `--help` wins over other errors: `apriori verify --help` exits 0 even though `--specs`/`--test-cmd` are absent.
- S7. `init` with no flags on a TTY still enters the interactive multiselect (parseStrict passes empty flags through); `init --tools` at end of argv without a value → exit 2.
- S8. Zero new dependencies; the dispatcher's existing top-level behaviors (`apriori`, `apriori --help`, `apriori -v`, unknown sub) are unchanged.
- S9. Repeats: `verify --specs a --specs b --test-cmd t` demands scenarios from BOTH targets; `status --change a --change b` uses `b`; `check --self --self` behaves as one `--self`.
- S10. Multi stop rule: `verify --specs a -x --test-cmd t` → exit 2 naming `-x` (never consumed as a spec target).
- S11. Empty multi: `verify --specs --test-cmd t` and trailing `verify --specs` → exit 2 naming `--specs`.
- S12. Alias: `init -y` behaves as `--yes`; `-h` as `--help` on every subcommand.
- S13. `apriori new a b` → exit 2 naming `b` (the declared change from today's silent ignore); `apriori stamp --foo` → exit 2 naming `--foo` (declared change from today's positional interpretation).

## Out of scope (won't do)

- `--json` for subcommands that lack it; any new flags.
- Long-form docs (item 7's job); this change only guarantees every usage string is reachable via `--help`.
- Shell completion.
- Changing any KNOWN flag's semantics.

## Decisions proposed

- DS-1: strictness is fail-closed alignment — the typo'd-flag-verifies-the-wrong-thing case is the same defect class 3.0.1 exit-code work fixed; silent ignore on a gate command is a correctness hazard, not a convenience.
- DS-2: usage strings live with each subcommand (single source: the same string `--help` prints is the one error paths print).
