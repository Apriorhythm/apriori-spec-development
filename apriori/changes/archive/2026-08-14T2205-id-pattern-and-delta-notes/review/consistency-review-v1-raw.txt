function cli(argv) {
  return withStrict(argv, { sub: 'doctor', usage: USAGE, positionals: 0,
    flags: { '--test-cmd': 'value', '--no-run': 'flag', '--cwd': 'value', '--json': 'flag' },
    jsonError: (m) => JSON.stringify({ result: 'UNUSABLE', findings: 0, checks: [], errors: [m] }, null, 2) }, (f) => {

    const res = runDoctor(a);
    if (a.json) { console.log(JSON.stringify(toJson(res), null, 2)); return res.code; }
    for (const e of res.errors) console.error('doctor: ' + e);
    const mark = { ok: '✓', finding: '✗', 'n/a': '–' };
    for (const c of res.checks) console.log(`${mark[c.status]} ${c.id} ${c.detail}${c.fix ? `  → ${c.fix}` : ''}`);
    console.log(res.code === 2 ? '\nDOCTOR: UNUSABLE (see errors)'
      : res.findings ? `\nDOCTOR: ${res.findings} finding(s)` : '\nDOCTOR: HEALTHY');
    return res.code;
  });
}

## 2. Inconsistencies

### IMPL-1 — SR-08’s universal compatibility guarantee has a weak oracle

- **Description:** SR-08 says that for every title bound by the old pattern, the new pattern binds the byte-identical ID. The test exercises only five simple examples, all consisting of a basic ID followed by whitespace and prose. It does not inject meaningful boundary variants such as end-of-input, punctuation, a following hyphen, long letter/digit runs, or generated combinations of valid old IDs and trailing characters.
- **Risk:** med
- **Why it matters:** A regression in `leadId`, anchoring, or the trailing-character rule could pass these examples while violating the compatibility guarantee.
- **Suggested fix:** Add a generated or bounded-exhaustive compatibility test. Generate old-pattern IDs across varied letter and digit lengths, combine them with EOF and representative trailing characters, retain only titles for which old `leadId` returns non-null, and assert the new result is strictly equal. Include punctuation, whitespace, hyphen, lowercase, uppercase, digits, and underscore after the old ID.

### IMPL-2 — CF-12 does not independently pin all three template occurrences

- **Description:** The implementation correctly updates the VALUE cell, DEFAULT cell, and adjacent built-in-default comment. The tests do not prove that contract. The new textual check merely rejects some stale literals and confirms that the current default occurs somewhere. The pre-existing parsing test compares the parsed VALUE against `lib/config.js`’s `DEFAULT_ID`, making production code the expected-value oracle. Neither test requires the DEFAULT cell and comment to exist and carry the exact frozen pattern.
- **Risk:** med
- **Why it matters:** Removing or corrupting the DEFAULT cell or comment could leave the suite green. Changing both production constant and template to an unintended value could also evade an independent specification oracle.
- **Suggested fix:** Assert the literal frozen source independently, split the `id-pattern` row, and check the VALUE and DEFAULT cells separately. Also locate the adjacent comment and assert its built-in-default wording contains the same exact source. Retain the existing parse and pipe-integrity assertions.

### IMPL-3 — CF-18’s “end to end” test stops before the critical paths

- **Description:** The CF-18 test runs `init` and obtains `origin: 'config'`, but then writes a separate temporary spec and calls `collectScenarios` with `new RegExp(resolved.source)` directly. It does not exercise TAP descriptions through `makeIdMatcher`’s config-origin child. It also does not establish agreement among CK-04, D6, verify, and gate C1 on the freshly initialized project.
- **Risk:** high
- **Why it matters:** The scenario exists to catch a template row that behaves differently from the built-in default or is consumed inconsistently. Direct in-process regex matching bypasses the highest-risk config-origin execution path and could miss a production failure affecting every newly initialized project.
- **Suggested fix:** Build one fresh initialized project containing all three specified title shapes and matching TAP descriptions. Exercise verify through the actual config-origin child, then invoke check, doctor D6, and gate C1 against the same project and assert their specified common conclusion.

### IMPL-4 — DR-19’s structural non-consumption assertion is brittle

- **Description:** The runtime tagged-skip assertion correctly exercises the concrete failure mode. The structural assertion slices source text between `classifyProbe` and `runDoctor` and looks only for the token `DEFAULT_ID`. It would pass if `classifyProbe` delegated to a helper that consumed `DEFAULT_ID`, or if the shared default reached the classifier under another identifier.
- **Risk:** med
- **Why it matters:** DR-19 makes a structural “never” guarantee intended to keep D5 independent of all future scenario-ID vocabulary changes.
- **Suggested fix:** Add a behavioral dependency-isolation test: load doctor with an adversarial replacement for the exported config default and demonstrate that the same probe classification is unchanged. Alternatively, introduce a narrow injectable classification-pattern seam and assert D5 receives only the frozen D5 pattern. Keep the existing tagged-skip test because it exercises the real historical failure mode.

### IMPL-5 — DR-20 does not pin the complete diagnostic contract

- **Description:** The tests establish one finding per class and nominally limit samples to no more than three. They do not assert that the selected samples are the first three in store order, that later samples are absent, or that each rendered sample is capped at exactly 40 characters. The current truncation check only rejects a run of 60 `x` characters, so substantially longer-than-40 samples could pass. The pattern-mismatch detail is checked for the word `config`, but not for the bounded pattern source itself.
- **Risk:** med
- **Why it matters:** Diagnostic regressions could produce unordered, overly long, or incomplete output while the scenario remains mechanically bound and green.
- **Suggested fix:** Use distinguishable titles longer than 40 characters. ## 2. Inconsistencies

### IMPL-1 — SR-08’s universal compatibility guarantee has a weak oracle

- **Description:** SR-08 says that for every title bound by the old pattern, the new pattern binds the byte-identical ID. The test exercises only five simple examples, all consisting of a basic ID followed by whitespace and prose. It does not inject meaningful boundary variants such as end-of-input, punctuation, a following hyphen, long letter/digit runs, or generated combinations of valid old IDs and trailing characters.
- **Risk:** med
- **Why it matters:** A regression in `leadId`, anchoring, or the trailing-character rule could pass these examples while violating the compatibility guarantee.
- **Suggested fix:** Add a generated or bounded-exhaustive compatibility test. Generate old-pattern IDs across varied letter and digit lengths, combine them with EOF and representative trailing characters, retain only titles for which old `leadId` returns non-null, and assert the new result is strictly equal. Include punctuation, whitespace, hyphen, lowercase, uppercase, digits, and underscore after the old ID.

### IMPL-2 — CF-12 does not independently pin all three template occurrences

- **Description:** The implementation correctly updates the VALUE cell, DEFAULT cell, and adjacent built-in-default comment. The tests do not prove that contract. The new textual check merely rejects some stale literals and confirms that the current default occurs somewhere. The pre-existing parsing test compares the parsed VALUE against `lib/config.js`’s `DEFAULT_ID`, making production code the expected-value oracle. Neither test requires the DEFAULT cell and comment to exist and carry the exact frozen pattern.
- **Risk:** med
- **Why it matters:** Removing or corrupting the DEFAULT cell or comment could leave the suite green. Changing both production constant and template to an unintended value could also evade an independent specification oracle.
- **Suggested fix:** Assert the literal frozen source independently, split the `id-pattern` row, and check the VALUE and DEFAULT cells separately. Also locate the adjacent comment and assert its built-in-default wording contains the same exact source. Retain the existing parse and pipe-integrity assertions.

### IMPL-3 — CF-18’s “end to end” test stops before the critical paths

- **Description:** The CF-18 test runs `init` and obtains `origin: 'config'`, but then writes a separate temporary spec and calls `collectScenarios` with `new RegExp(resolved.source)` directly. It does not exercise TAP descriptions through `makeIdMatcher`’s config-origin child. It also does not establish agreement among CK-04, D6, verify, and gate C1 on the freshly initialized project.
- **Risk:** high
- **Why it matters:** The scenario exists to catch a template row that behaves differently from the built-in default or is consumed inconsistently. Direct in-process regex matching bypasses the highest-risk config-origin execution path and could miss a production failure affecting every newly initialized project.
- **Suggested fix:** Build one fresh initialized project containing all three specified title shapes and matching TAP descriptions. Exercise verify through the actual config-origin child, then invoke check, doctor D6, and gate C1 against the same project and assert their specified common conclusion.

### IMPL-4 — DR-19’s structural non-consumption assertion is brittle

- **Description:** The runtime tagged-skip assertion correctly exercises the concrete failure mode. The structural assertion slices source text between `classifyProbe` and `runDoctor` and looks only for the token `DEFAULT_ID`. It would pass if `classifyProbe` delegated to a helper that consumed `DEFAULT_ID`, or if the shared default reached the classifier under another identifier.
- **Risk:** med
- **Why it matters:** DR-19 makes a structural “never” guarantee intended to keep D5 independent of all future scenario-ID vocabulary changes.
- **Suggested fix:** Add a behavioral dependency-isolation test: load doctor with an adversarial replacement for the exported config default and demonstrate that the same probe classification is unchanged. Alternatively, introduce a narrow injectable classification-pattern seam and assert D5 receives only the frozen D5 pattern. Keep the existing tagged-skip test because it exercises the real historical failure mode.

### IMPL-5 — DR-20 does not pin the complete diagnostic contract

- **Description:** The tests establish one finding per class and nominally limit samples to no more than three. They do not assert that the selected samples are the first three in store order, that later samples are absent, or that each rendered sample is capped at exactly 40 characters. The current truncation check only rejects a run of 60 `x` characters, so substantially longer-than-40 samples could pass. The pattern-mismatch detail is checked for the word `config`, but not for the bounded pattern source itself.
- **Risk:** med
- **Why it matters:** Diagnostic regressions could produce unordered, overly long, or incomplete output while the scenario remains mechanically bound and green.
- **Suggested fix:** Use distinguishable titles longer than 40 characters. Assert the exact first three rendered prefixes in store order, each with length at most 40, and assert that samples four through six are absent. Assert the exact bounded pattern source and exact origin in the mismatch detail.
