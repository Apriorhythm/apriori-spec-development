# Delta — archive-merge (archive-drop-guard)

## MODIFIED Requirements

### Requirement: the modified-block integrity engine reports replacement fidelity
A pure shared helper SHALL compare a MODIFIED operation's old store block against its replacement (both captured at the projection's own parse snapshot — `buildProjection` additionally returns the raw old/new block text pairs per MODIFIED operation; no consumer re-reads files) and report structural fidelity. The report is informative for `retained`, `titleChanged`, `added` and `missingLines`; since archive-drop-guard the `dropped` and `ambiguous` classes are CONSUMED by the archive's drop guard (see "archive never drops a store scenario without a fingerprint-bound owner decision"), so a MODIFIED replacement that drops or cannot pair a scenario is refused instead of merged. Structure scan: the requirement heading line never participates; requirement prose runs from the line after the heading to the first VALID scenario heading (state A's actual regex `/^####\s+Scenario:\s+(.*)$/m`, fence-aware exactly like `stripFences` — only lines inside CLOSED triple-backtick pairs are not delimiters; an unclosed opener is ordinary text and later headings still split); fence delimiter lines and fenced non-empty lines are compared as body lines. Pairing runs per key (scenario ID when present, normalized full title otherwise) through one cardinality truth table — o=0,n=1 added; o=1,n=0 dropped; o=1,n=1 paired (same normalized title → retained, different → titleChanged, mutually exclusive, both body-compared); any side >1 → ambiguous (side old/new/both with counts; the key skips every other class and body comparison). Line comparison is ONE algorithm: order-preserving greedy subsequence over normalized non-empty lines (CRLF/CR→LF, trailing whitespace stripped, leading whitespace stripped; duplicates consumed by count); unmatched OLD lines are `missingLines` (requirement prose misses carry scenario=null; only old-content loss is reported). An idempotent replacement takes a FAST PATH — `oldBlock.trim() === newBlock.trim()` short-circuits before any structure scan or id extraction — yielding an entry whose diff arrays are all empty (the stamped-rerun repair path included: a repaired module still contributes its equal-text pair, one entry per MODIFIED operation always). Capture points are module-level testable: `buildProjection().modifiedBlocks` carries raw text pairs — for rename-then-modify the oldBlock deep-equals the COMPLETE pre-rename block (captured before the rename key swap) and the newBlock deep-equals the delta block. The human formatter renders SAFELY: every externally-sourced field (titles, lines, requirement names, file suffixes, ambiguous keys) has C0/DEL control characters replaced with `·` BEFORE the 120-unit truncation (JSON keeps full raw text; JSON.stringify escapes there); an all-empty result renders as NOTHING (no blank line).

#### Scenario: AM-43 the cardinality truth table classifies every occurrence
- WHEN an old block carries KV-01/KV-02/KV-03 and the replacement carries KV-01 (same title), KV-03 (changed title), KV-04 — and separately each of the eight o/n cardinality rows is exercised (including a duplicated KV-05 on one side and no-ID title keys)
- THEN retained=[KV-01], titleChanged=[KV-03 with old/new titles], dropped=[KV-02], added=[KV-04]; each truth-table row lands in its one class; ambiguous entries carry {key, side, oldCount, newCount} and skip every other class; ambiguous ordering is old-present keys by old first occurrence, then new-only keys by new first occurrence

#### Scenario: AM-44 the subsequence comparison reports lost lines faithfully
- WHEN a retained scenario's replacement drops one AND clause, reorders two lines, repeats a line fewer times, differs only in indentation/trailing whitespace on another, and the requirement prose loses a sentence
- THEN missingLines lists the dropped AND clause, the reordered-out line and the under-repeated line (by count) with full original text, the whitespace-only difference is NOT reported, and the prose loss carries scenario=null

#### Scenario: AM-45 structure boundaries follow state A exactly
- WHEN a rename-then-modify replacement preserves prose and scenarios verbatim under the new requirement name, a CLOSED fence contains a scenario-looking heading, an UNCLOSED fence precedes a real scenario heading, and a heading uses multiple spaces after `####`
- THEN the rename case reports zero missingLines (the heading line is never compared); the fenced fake heading does not split a scenario and its lines are body-compared; the heading after the unclosed opener still splits (stripFences strips only closed pairs); the multi-space heading is a valid delimiter

#### Scenario: AM-46 archive prints the integrity section; a dropped scenario is refused until the owner names it
- WHEN `apriori archive --change <name>` passes preflight with a MODIFIED delta whose replacement drops a scenario — on dry-run and on `--write` — and separately with a replacement that only rewrites a body line
- THEN the human integrity section appears BEFORE the result line in both cases; the dropping run is REFUSED (`RESULT: REFUSED — nothing written`, exit 1) with the `— DROPPED SCENARIOS —` block and its manifest fingerprint, the store untouched; the body-rewrite run merges exactly as before with its `! missing` line and no dropped block; and ANY preflight failure — malformed, CAS, conflict, denial, a pre-existing temp file, an escaping --changes-dir destination — prints NO integrity section

#### Scenario: AM-47 the archive id-pattern channel is resolved, terminable and fail-closed
- WHEN archive runs with a custom config `id-pattern` row recognizing letter-suffixed IDs; with no row (default); with an uncompilable row; with an injected matcher whose batch fails only at the integrity stage; and programmatically with no factory at all
- THEN the custom row pairs the retitled scenario by ID (`titleChanged`) through the resolved pattern; with no row the built-in default cannot bind those IDs and the structural preflight refuses (exit 1, `scenario without a bindable id`, no integrity section); an uncompilable row makes the structural preflight refuse with one sanitized `archive: the structural check could not run — process-config id-pattern row is invalid …` line (≤260 UTF-16 units, control characters replaced) and `RESULT: FAILED PREFLIGHT — nothing written` — there is no warning-and-skip for a broken channel; the pinned seam `archiveMerge.cli(argv, deps)` / `archiveChange({..., idMatcherFactory})` accepts an injected factory `(cwd) => matcher | {error}`, and without one the module composes the controlled matcher itself, lazily, from `lib/config`'s resolveIdPattern plus spec-runner's makeIdMatcher (no top-level require — the module graph stays acyclic), so the preflight AND the integrity section run; a matcher that fails only at the integrity stage prints exactly one sanitized stderr line `warning: modified-integrity <reason>`, skips the report, and — since archive-drop-guard — refuses the run when any MODIFIED old block carries a scenario (a guard that cannot see must not wave a deletion through) while merging as before when none does

### Requirement: --force overrides progress only, on pre-recorded human authority
`--force` SHALL belong to the high-level form alone and SHALL override ONLY progress blockers, which are exactly two things: a review family's escalation the owner already answered (its `reframe` record), and — since archive-drop-guard — the dropping of store scenarios the owner already named through a fingerprint-bound `archive-drop` record. Everything else is non-forceable: an ambiguous MODIFIED replacement, a drop with no decision or with a decision whose fingerprint no longer matches the input, every R1 outcome (`abandoned` above all), every structural defect (`io-error`, `symlink`, `not-file`, `not-dir`, `escape`, `bad-ancestor`), a review family stopped at its round limit (or by an `escalate` verdict) with no owner decision on record (readiness reports it `forceable: false` while still naming the reframe cure; it turns forceable only once the decision is recorded), an invalid `review-round-limit` configuration, a `review-progress` record that is missing or fails its structural check, an unmet review floor, and every R5 refusal — an open item nobody accepted is not progress, and owner acceptance for it is spent in the state, not at the command line. There is no `tasks` force class and no live `ledger` class: the `archive-force ledger` grammar is still PARSED — the SAME entry, and the same parser, the item acceptance and the `reframe` decision use — but a grant is reported as `note: archive-force has nothing left to force in 6.2` and overrides nothing. Revocation is by APPENDING `archive-force-revoke ledger <reason>` and the last decision wins, for that note alone. The limit-stop DOUBLE action is preserved: the recorded `reframe` alone is not a `--force`, and `--force` alone is not a decision.

#### Scenario: AM-89 an archive-force record is inert: nothing is forced, and the note says so
- WHEN a bundle records the canonical `archive-force ledger — <reason>` beside an open ledger row, with and without `--force`, and then a revoked grant, an `archive-force tasks` record, a `note:` near miss and no record at all
- THEN the first archives either way with `note: archive-force has nothing left to force in 6.2` and no `forced:` line, the unread row never reaches the report, and the other four print nothing about `archive-force`

#### Scenario: AM-87 nothing but the answered limit escalation and the named drop is forceable
- WHEN the blocker is any R1 outcome, a structural flow-state defect, or a pending open item — each beside a standing `archive-force ledger` record
- THEN `--force` does not change the refusal, no force advice is printed for the item, and readiness reports it `forceable: false` with nothing forced

#### Scenario: AM-110 the kept parser is anchored: only the canonical entry is a grant
- WHEN the entry reads `archive-force ledger — cleanup deferred`, or `archive-force ledger2 …`, or `archive-force-2 ledger …`, or `do not archive-force ledger — 还没做完`, or the canonical payload under a `note:` / `producer:` / `agent:` / `gate⑤ (owner):` actor, or with no timestamp, or with no em dash, or with no reason
- THEN `forceGrant` answers a grant for the first only — the class word inside a reason never authorizes, a keyword preceded by free text never authorizes, and the entry's PREFIX is as binding as its payload; a Chinese reason is a reason

#### Scenario: AM-111 revocation appends and the last decision wins — in the parser and in the note
- WHEN `archive-force ledger <reason>` is followed by `archive-force-revoke ledger <reason>` and later by another `archive-force ledger <reason>`, each carrying a reason
- THEN the parser answers granted, then not, then granted again, in the order the entries appear, and the archive prints the nothing-left-to-force note exactly when the parser answers granted; a revoke with no grant before it grants nothing, and a revoke carrying no reason is ignored exactly as a reasonless grant is

#### Scenario: AM-91 the single-file form does not take --force
- WHEN `--force` accompanies `--store`/`--delta`
- THEN archive exits 2 with usage

#### Scenario: AM-116 one canonical owner entry supplies the payload for every decision verb
- WHEN `ownerPayload` is applied to the canonical entry for each of the three verbs, and then to the same payloads under a `note:` / `producer:` / `agent:` / `gate⑤ (owner):` / `ownership:` actor, with no timestamp, and with a timestamp-shaped non-timestamp (a 13th month, a 24th hour, a 60th minute)
- THEN the canonical forms yield their payload and every other form yields `null`, so the verb patterns below never see a non-owner entry; a NEGATED verb still yields a payload, because refusing it is the verb pattern's job — the keyword has to open the payload

#### Scenario: AM-117 the usage lines say which flags belong to which form
- WHEN `apriori archive` is run with no arguments
- THEN the single-file line carries neither `--changes-dir` nor `--force`, and the high-level line carries both — the two forms are no longer symmetric and the usage must not pretend otherwise

## ADDED Requirements

### Requirement: archive never drops a store scenario without a fingerprint-bound owner decision
When any MODIFIED replacement of the change drops a store scenario (the integrity engine's `dropped` class, paired by scenario ID — a title change under the same ID is not a drop), `apriori archive --change <name>` SHALL refuse in dry-run and `--write` alike with `RESULT: REFUSED — nothing written` (exit 1), nothing staged, nothing moved. It SHALL print a `— DROPPED SCENARIOS —` block listing every deletion as `<file> · <requirement> · <scenario id or title>` (sorted) and the manifest fingerprint, and on stderr the copyable cure `- <YYYY-MM-DDTHH:MM> owner: archive-drop <change> sha256:<fingerprint> — <reason>`. The fingerprint is the SHA-256 of a canonical manifest built from the projection's own parse snapshot (never a second read): `apriori archive-drop manifest v1`, the target change name, every touched module's store digest and delta digest (`fingerprint()` of the raw text, `new` for an absent store), and the sorted deletion locators — so editing any delta or store of the change, or dropping a different set, moves the fingerprint and voids the decision. Release requires BOTH a canonical owner entry whose target and fingerprint match exactly (same parser and strictness as the other decision verbs: real timestamp, actor `owner`, em dash, a reason; last matching entry wins) AND explicit `--force`; the decision alone refuses naming the missing flag, the flag alone refuses naming the missing decision, and a forced run prints `forced: dropped <n> scenario(s) — owner decision on record: <entry>`. An `ambiguous` key (a scenario key occurring more than once on either side) SHALL be refused as not forceable — disambiguate first; `missingLines` stays report-only (requirement-prose loss and scenario-body loss are S4's remaining, still-open gap). When the modified-block comparison cannot run at the integrity stage (after the structural preflight passed) and some MODIFIED old block carries a scenario, the run SHALL be refused (a guard that cannot see must not wave a deletion through); old blocks with no scenario need no matcher. Manifest fields SHALL be JSON-encoded and the manifest hashed byte-for-byte (no line-ending normalization of the manifest itself), while the store and delta content digests keep `fingerprint()`'s LF/CRLF normalization; an existing but empty store contributes its content digest, `new` marks only an absent store. The single-file form (`--store/--delta`) has no bundle to hold a decision: it SHALL refuse any dropping or ambiguous replacement outright and point at the high-level form, while merging title changes and body rewrites as before. `--force` remains a high-level-form flag; no ratio or threshold configuration key is introduced.

#### Scenario: AM-123 a delta that drops a store scenario is refused with zero writes, and the report names the deletion, its fingerprint and the cure
- WHEN a MODIFIED replacement omits scenario KV-02 of the store block, on dry-run and on `--write`
- THEN both runs exit 1 with `RESULT: REFUSED — nothing written`, print `— DROPPED SCENARIOS —` with `m/spec.md · R-K · KV-02` and `manifest sha256:…`, put the `archive-drop` cure line on stderr, leave the store byte-identical, no `.tmp-archive` artifact anywhere under the store root, and the bundle in place; `dropManifest` over the projection's `sources` and integrity entries reproduces the printed fingerprint from a text of exactly `apriori archive-drop manifest v1` / `target: "c"` / `store "…": …` / `delta "…": …` / `drop "…" "…" "…"` lines (JSON-encoded fields)

#### Scenario: AM-127 the manifest binds fields unambiguously and the content digests normalize line endings
- WHEN two changes are identical except that one file suffix or requirement name differs only by an embedded control character; when the same delta is stored with CRLF instead of LF; when a touched store exists but is empty versus absent; and when two `archive-drop` decisions for the same target are on record with only the last one matching
- THEN the control-character variants yield different fingerprints (fields are JSON-encoded, the manifest is hashed unnormalized); the CRLF delta yields the same fingerprint as the LF delta (content digests normalize); the empty store hashes as content while the absent one reads `new`, so the two fingerprints differ; and the last matching decision wins — its full entry appears in the `forced:` line

#### Scenario: AM-124 the double action: a fingerprint-bound owner decision AND --force merge; either alone, a stale fingerprint, or a non-owner actor refuse
- WHEN the canonical `archive-drop c sha256:<printed fingerprint> — <reason>` entry is on record and `--write --force` is passed; then the entry without `--force`; then `--force` without the entry; then the same entry after the delta drops a second scenario; then after the store gained a scenario; then the payload under `note:` / `agent:`, for another target, and with no reason
- THEN the first merges (KV-02 gone, `forced: dropped 1 scenario(s) — owner decision on record: …`), the second refuses naming the missing flag, the third refuses naming the missing decision, the stale-fingerprint cases refuse (the decision no longer names this input), and none of the non-canonical entries authorizes; `dropGrant` answers a grant for the exact target+fingerprint only and `null` for a mismatching fingerprint or a reasonless entry; a valid decision plus `--force` still refuses when another rule refuses (a pending `## Open` item ⇒ R5 `NOT READY`, store untouched) — the authorization bypasses nothing but the drop

#### Scenario: AM-125 a title change or a body rewrite is not a drop; an ambiguous key is refused and never forceable
- WHEN a replacement retitles KV-01 (same ID) and rewrites KV-02's body; and separately the store block carries KV-01 twice and the replacement carries it once
- THEN the first merges with no decision, reporting `titleChanged` and no dropped block; the second is refused as `scenario key 'KV-01' is ambiguous (old; old 2/new 1) — … not forceable` in dry-run and `--write`, with or without a decision and `--force`, the store untouched

#### Scenario: AM-126 the single-file form never drops a store scenario and points at the high-level form
- WHEN `apriori archive --store <f> --delta <f> --change c` is run with a replacement that drops KV-02, dry-run and `--write`; then with a retitling replacement
- THEN the dropping runs exit 1 with `RESULT: REFUSED — nothing written` and a stderr line naming the scenario and the high-level form, the store byte-identical; the retitling run merges as before
