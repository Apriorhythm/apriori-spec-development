# Delta — protocol (scope-disposition)

## MODIFIED Requirements

### Requirement: there is no ledger — `## Open` is the only home of open issues, and one thing blocks
The runbook (both editions) SHALL document that there is no issue ledger: the state's `## Open` section is where a change's open substantive issues live, one `- <ID>: <text>` line each, and it is the only place `gate`, `archive` and `status` read them (`review/issues.md` is never opened, and nothing in it blocks or is reported). A re-found issue REOPENS its old id — reopened is an event, not a new line. EXACTLY ONE thing blocks a delivery: a pending item — one nobody has accepted and that is not a registered follow-up (`- <ID>: follow-up → <new-change-name> — <text>`, a new ask the delivery does not depend on, reported as a note and never closed by being moved out); an accepted item is reported as still present and never deleted by a tool. The retired ledger vocabulary and its setters SHALL NOT be documented. Only correctness, security and stated-requirement gaps become pending items at all — a new ask with no delivery dependency is a follow-up item, not a pending one; everything else is `advisory`, and the label is the reviewer's exclusive call; R1's unresolved delivery obligations and R4's review stops keep their authority. The concepts handbook mirrors the same rules in both languages, and neither runbook lists the ledger file as an artifact.

#### Scenario: PR-18 there is no ledger: ## Open is the only home of open issues, and one thing blocks — in both editions
- WHEN the §5 prompts section is read in either language
- THEN `## Open` is named as the only home of open issues, `review/issues.md` is stated to be never opened, the reopen-is-an-event rule is stated, exactly one blocking thing (a pending item: unaccepted and not a registered follow-up) is named, the retired vocabulary is absent, the artifact table carries no ledger row, and the concepts handbook says the CLI reads no ledger in both languages

## ADDED Requirements

### Requirement: the runbook states the per-finding disposition rule
Both runbook editions SHALL carry, in §4 Review & Deliver, a disposition rule for review findings: scope is judged per finding, never by volume; each substantive finding gets a disposition with its basis (current contract / existing constraint / new ask); the necessary-fix criterion — left alone, the delivered product would violate a locatable accepted acceptance condition, a valid owner decision or an applicable existing constraint, cited with the evidence of the violation; a necessary fix is never moved out for its size (split the implementation, keep the dependency); changing a commitment is the owner's decision and its blocking stands until recorded; a new ask the delivery does not depend on is registered as a follow-up with the stable landing grammar `- <ID>: follow-up → <new-change-name> — <text>`, reported as a note and never closed by being moved out; `fixed` / `contract` / `follow-up` / `invalid` / `duplicate` are recommended words, not a closed vocabulary, and an unresolved finding keeps its id, impact and next action; `approach:` in `review-progress` is not a second ledger. §5's rule on what blocks SHALL distinguish a pending item from a registered follow-up in both editions, and the CLI reference SHALL say a registered follow-up is a note; the landing spot SHALL be a valid change name other than the change itself, and the runbook SHALL say how a later authorized session carries the original id into that change. The P3 prompt is NOT changed (RIB-10 pins it verbatim by a recorded human ruling): the disposition is the producer's duty. Evidence: plan/01 S6 (review-driven scope creep with no gate, ≥5 cases across 5.1/5.2) and the Claude × Astra plan consensus (序 3), which rejected a closed vocabulary and a C8 marker check in favour of this minimal protocol.
