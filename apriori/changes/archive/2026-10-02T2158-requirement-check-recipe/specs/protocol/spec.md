# Delta — protocol (requirement-check-recipe)

## MODIFIED Requirements

### Requirement: every /goal recipe names the human stop as a second terminal outcome
Each `/goal` recipe in `docs/operator.md` — Specify, Build & Test, Review & Deliver, Build → Review → Archive, and the requirement-level independent check — SHALL carry in its goal condition itself a second outcome: the agent stopped at a human stop (§1 R1; for every recipe that runs Build & Test — Build & Test and Build → Review → Archive — also the 25-turn bound) and its last message names the stop, what is still open and the decision the owner must make — an outcome that hands the change back and is never a pass or a delivery (the requirement-level check also ends at an actual capability block or a set execution bound, and hands the requirement back). `docs/operator_cn.md` SHALL carry the same recipes verbatim. The concepts handbook (both languages) SHALL say why: the evaluator judges only the condition it was given, so a stop listed only in the goal's body keeps the loop answering "not yet met".

- THEN each recipe's goal sentence carries "OR you stopped at" a human stop with the last message naming it, what is still open and the decision the owner must make, and says that outcome hands the change (for the requirement-level check, the requirement) back and is never a pass or a delivery; every recipe bounded at 25 turns names that bound in its condition; the Chinese operator guide carries the identical recipe text; and both concepts editions explain that a stop listed only in the body does not end the loop

## ADDED Requirements

### Requirement: the operator guide carries an optional requirement-level independent check, landing beside the requirement's sources
`docs/operator.md` SHALL carry, and `docs/operator_cn.md` SHALL carry with the identical recipe block and a Chinese explanation, an optional recipe for checking a requirement end to end after its last change is archived, when one requirement was split into several changes: run by a reviewer independent of the session that built the code (a different model or a fresh session, as R2 asks of P3); its inputs listed apart from P3's default input (the sources with their versions, the archived contracts of the requirement's changes, the owner's recorded decisions, the source checklist); the reviewer reconciles every `in` checklist row (corrected rows against their ruling), traces the end-to-end paths across the changes, checks every delivery dependency handed outside the workflow, and checks the assertion and run conditions behind each tick, and reads the code without fixing it. The report, every re-check and the one current checklist SHALL land in the requirement's document directory — never in an archived bundle and never in a change's `review/` — and the report SHALL pin the code commit, source versions and scope. Findings follow §4's disposition: a necessary fix in one or more changes, each registering the report in Ground, carrying the finding's id and passing its own P3, then a re-check of the fixes by the requirement-level reviewer written back to the requirement directory, the two closing separately, an earlier check's conclusions never P3's default input; a follow-up with its landing spot; an owner call pending. A clean check opens no change and keeps its report and checklist. The recipe's goal is complete only when the agreed scope is checked, every necessary fix and its re-check are closed, every follow-up has its landing spot, nothing blocking is open and the owner has the report; otherwise the agent continues within its delegation, and only at a human stop, an actual capability block or a set execution bound hands the requirement back, never as a delivery. An optional owner acceptance walk (a script from the checklist and contracts with visible expectations, a kit with seed data, commands, a guard before real side effects and cleanup, real side effects only with one-shot authorization, problems recorded first and classified after) may follow. No machine check is added.

- THEN each carries the explanation (independent reviewer; inputs apart from P3's default input; the report, re-checks and the one current checklist in the requirement's document directory, never in an archived bundle or a change's `review/`; the commit, source versions and scope pinned; fixes per §4 in one or more changes with their own P3 and a separate re-check; a clean check opening no change; the optional owner acceptance walk with its kit, guard, one-shot authorization and record-then-classify) and the identical fifth recipe block, whose goal is complete only with the scope checked, fixes and re-checks closed, follow-ups landed, nothing blocking open and the owner reported to — otherwise continuing within the delegation and handing the requirement back only at a human stop, a capability block or an execution bound

### Requirement: the guide keeps a requirement-level check's checklist beside the requirement's sources
`guides/prototype-walk.md` SHALL say that a requirement-level check, run after the requirement's last change is archived, keeps its successor checklist in the requirement's document directory — not in any change — and that from then on it is the one current checklist, referenced and never copied by the changes that carry the fixes; and that a later reconciliation fills `implementation` and `verification` there.

#### Scenario: PR-68 the guide places a requirement-level check's successor in the requirement's directory
- WHEN §5 and §9 of `guides/prototype-walk.md` are read
- THEN §9 names the requirement-level check as the one exception to where a successor lives — the requirement's document directory, the one current checklist from then on, referenced and never copied by the fix changes — and §5's reconciliation rule points there for a requirement-level check

## Notes

Why: the 2026-10-02 analysis of requirement 5.9 found that the per-change reviews (each judging one change against its own contract) left issues a later whole-requirement review found; the owner ran that review outside apriori. The Claude × Astra consensus (R59-CONSENSUS §三 batch 2, §五) makes it an optional operator recipe — not a default step and not a machine check — that consumes the prototype-walk checklist (prototype-walk-guide) and guards against green ticks that prove nothing. Its landing place came from a problem met while drafting: the check runs after the last change is archived, archived bundles are frozen, and a change with no delta cannot pass review-ready, so the report, the re-checks and the one current checklist live beside the requirement's sources (consensus §五, rounds 8–10, DISAGREEMENTS 0). Nothing here claims the check saves cost or that it would catch any particular class of defect.
