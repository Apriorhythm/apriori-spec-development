# Delta — protocol (batch-review-fixes)

## MODIFIED Requirements

### Requirement: executable specs shrink verification and drop the OpenSpec adapter
The V3 runbook SHALL make scenario-to-test binding a deterministic gate, narrow the heterogeneous consistency review to what binding cannot prove, implement archive natively, and remove the OpenSpec adapter so the interface is single-path plain-files.

#### Scenario: PR-01 the Build & Test exit adds a deterministic spec-runner gate
- WHEN a change reaches the Build & Test exit
- THEN "spec-runner reports GREEN (every scenario BOUND-GREEN)" is a required exit condition, alongside the existing test/lint conditions

#### Scenario: PR-02 P8 scope narrows to semantic faithfulness
- WHEN the consistency review (P8) runs on a change whose spec-runner is already GREEN
- THEN P8's mandate is narrowed to whether each test faithfully exercises its scenario's intent (binding/coverage is now mechanical, per the v2.2 judge-bias caveat), not re-checking coverage

#### Scenario: PR-03 archive action is native plain-files, no adapter
- WHEN the archive action runs
- THEN it uses archive-merge (AM-01..10) directly; there is no `openspec/` path and no `/opsx:` adapter command

#### Scenario: PR-04 the interface is single-path plain-files
- WHEN any runbook/README section references artifact paths
- THEN it names only the `apriori/` plain-files layout; no `(adapter: openspec/…)` dual-path parentheticals remain (CK-05 enforces this)

#### Scenario: PR-05 probe code is disposable and never becomes an artifact
- WHEN the runbook describes what to do when a fact will not yield to reading
- THEN probe code is allowed, thrown away afterwards and never a deliverable — its product is an `observed` line in the state's Reality Check, not an artifact the change carries; no `spike/` path and no separate prototype track survives in the runbook

#### Scenario: PR-06 a configurable language governs human-facing prose, machine tokens stay English
- WHEN the runbook describes output language
- THEN human-facing prose follows `process-config.md`'s `language` (unset/`auto` → match the human), while machine tokens (verdict lines, scenario IDs, ADDED/MODIFIED/REMOVED, file paths) stay English regardless

#### Scenario: PR-07 discuss-first is a short stance entered via P6, with no prescribed choreography
- WHEN the runbook describes what to do with an idea not yet stateable as one change
- THEN it offers a Discuss-first stance (a stance, not a tracked phase) entered via P6 in which the agent reads the real codebase, surfaces risks and unknowns and presents candidate approaches with their tradeoffs; nothing durable is written before the human's explicit approval (no code, no spec or design file, no `apriori new`, no flow-state), stated in one plain sentence; a task already stateable as one change starts directly and nobody is talked out of a task they already stated; and no diverge→converge ritual, one-question-per-message rule, coverage checklist or mockup-variant quota survives in the runbook or the handbook (retired by 6.2-sub-doc)

#### Scenario: PR-08 the four phases and the five decision points bind in the runbook
- WHEN the runbook's flow and hard-rule sections are read
- THEN §4 names exactly the four phases (Ground / Specify / Build & Test / Review & Deliver) with no numbered-step vocabulary, the state's `phase` key carries those four words plus `done` and `abandoned`, and §1 R1 names exactly five things that stop for a human — an escalation, an `## Open` item that cannot be resolved (critical evidence blocked, a pending item), a review family past its one automatic re-review (`reframe`), an external side effect, and abandonment — while stating that no consolidation authorization exists

#### Scenario: PR-09 discuss-first ends in two separate approvals and seeds the ONE state
- WHEN a discussion reaches its conclusion
- THEN nothing durable is written before the human approves; saving the conclusion and starting development are two separate approvals whose implication runs one way only (approval to develop carries the write development depends on, approval to save never reaches development); on approval the conclusion lands in the state's `## Reality Check` as the three Ground kinds — `decision` for what they approved, `observed` for what was actually read, `assumption` for what the slice leans on — with open questions as `## Open` items, `apriori new` run only when the change does not already exist, and a save-only approval stops before Ground

#### Scenario: PR-10 the E2E layer sits above the binding gate, and no project-type matrix survives
- WHEN the Build & Test section is read
- THEN it states that scenario IDs bind to `apriori verify` via unit/component tests (verify speaks TAP, which Playwright does not emit), that the Playwright E2E/visual layer is an additional exit condition above the binding gate whose visual checks emit a textual pass/fail, that implementation-time screenshots land in the gitignored `apriori/tmp/` while baseline images belong to the project's own test suite — and that there is NO per-project-type evidence table: what a change owes is the evidence the risks it actually hits call for, and whatever stays unverified is an `## Open` item

#### Scenario: PR-11 self-added promises are retracted or narrowed by default; established guarantees still need a success-path injection test
- WHEN a spec or KB asserts a hard guarantee — crash durability ("a success response means the write is persisted"), atomicity, or an invariant qualified "always" / "under concurrency" / "after restart" — or the producer adds such a promise or a mechanism of its own
- THEN Build & Test's self-added-promise discipline says that a promise with no established requirement, valid decision or actual safety responsibility behind it is retracted or narrowed to what is actually verified, by default, and that an established guarantee needs a test injecting the adversarial condition on its **success path**; P2 carries the same rule to the producer; the independent review (P3) lists an established hard guarantee with no such test, and looks for self-added promises and mechanisms beyond the requirement; and the runbook carries no generic fault-injection tutorial (no `fsync`, root/`chmod` or kill-after-ack recipe)

#### Scenario: PR-12 flow-state persists the reviewer's resumable session id
- WHEN a heterogeneous review starts and round 1 prints the reviewer's session id
- THEN the flow-state schema (§3) carries a `reviewer-session` field that records it immediately (so even a first-round interruption on either side resumes the SAME session per R2 rather than reconstructing it), and R2 names this field as the persistence point

#### Scenario: PR-13 the reviewer's default context is fixed, and it does not do the producer's job
- WHEN the independent review prompt is read
- THEN its default input is exactly the behavior contract, the diff, the `## Open` items and the uncovered boundaries; raw review transcripts, closed issues and other changes' documents are explicitly excluded; it asks for behavior the contract requires that the code implements only on the happy path, for the uncovered boundaries the `## Open` items themselves name, and for scope one evidence chain cannot prove; and it forbids the reviewer from compiling the code, adding the producer's missing tests one by one, or rewriting the approach — the answer to needing any of those is that the change was not review-ready

#### Scenario: PR-14 `/apriori` routes by intent, and the entry positions carry the same meanings
- WHEN a human uses `/apriori` with no arguments, with an explicit ask to discuss, with free text that does not identify a change to work on, or naming a change to work on
- THEN the scaffolded command routes on what the human asked for, not on whether the argument line is empty: work starts or resumes only when the text identifies one change to work on and does not limit the request to discussion, every other input enters Discuss first via P6, mentioning an existing change while discussing grants no development, and the exhaustiveness clause is the template's last routing rule; the runbook's §0, both READMEs and `apriori init`'s closing hint carry the same routing meanings

#### Scenario: PR-15 abandonment is a legal exit at any point, on the human's word only
- WHEN the human decides mid-change to drop a change (any phase)
- THEN the runbook prescribes: the human's verbatim reason recorded in `gates:`, the change dir archived with flow-state `phase: abandoned`, nothing written to KB or spec store, touched code disposed only as the human directs; the agent may never propose abandonment as an escape from failing reviews; whatever the change already wrote is kept as a recorded decision

#### Scenario: PR-16 legacy-project clarity clauses from the inherited-poll lab
- WHEN an agent runs the protocol on a legacy project or resumes a dead session
- THEN the runbook states: the KB pre-check is part of Ground and usually runs FIRST on a legacy kickoff; the `gates:` label vocabulary is exactly `owner` and `note`; the KB capture prompt declares capture is NOT a defect audit; the state's `## Next` carries at most three actions; R2's transcription mechanism covers the review doc itself; and the archive prose says `--write` moves the in-flight change dir to `apriori/changes/archive/<YYYY-MM-DDThhmm>-<name>/` by default, so a resumed session must look under `archive/` once the move has happened

### Requirement: an item marked as the owner's call stays the owner's, and words recorded for the owner are disclosed
§1 R1's owner-decision paragraph SHALL say that an item a review or an outside report marks as the owner's call — a scope, a caliber, a risk to accept — and that no valid owner decision covers yet is not decided by a broad instruction such as "fix everything else": it stays a pending `## Open` item until the owner answers it, and one answer may settle several such items when it names them (their ids, or "all the owner items as recommended"). It SHALL say that when the agent records in `gates:` a decision the owner gave elsewhere, it writes the owner's words and adds a `note:` saying it recorded them on the owner's behalf and where they came from; the note discloses and does not make the owner's anything they did not say (a reframe kind they did not name, the agent's reading of an ambiguous answer), so it says which parts are the agent's. The same paragraph, and §4's archive `--force` sentence, SHALL name the families `--force` can carry as the code derives them: an escalated review family — an `escalate` verdict, a round past its one automatic re-review that no owner release opened or that still revises, or a `revise` after the owner answered the limit round itself with a `reframe` — and only with the owner's decision already recorded. The CLI reference's archive `--force` paragraph (`docs/cli.md`, `docs/cli_cn.md`) SHALL name the same three forms.

#### Scenario: PR-64 a broad instruction does not decide an owner item, and recording for the owner is disclosed
- WHEN §1 R1's owner-decision paragraph, and the archive `--force` paragraph of both CLI reference editions, are read
- THEN it says an item marked as the owner's call with no valid owner decision is not decided by a broad instruction and stays a pending `## Open` item until the owner answers; that one answer may settle several when it names them; that a decision recorded on the owner's behalf carries a `note:` saying so and where the words came from, and says which parts are the agent's; and that the recorded decision plus `--force` applies to an escalated review family named by its three sources (an `escalate` verdict, a round past the one automatic re-review that no owner release opened or that still revises, a `revise` after the owner took the limit round with a `reframe`), in R1, in §4's archive sentence and in both CLI references alike — none speaks of a family "stopped at its limit" or keys `--force` on a round's position alone

### Requirement: every /goal recipe names the human stop as a second terminal outcome
Each `/goal` recipe in `docs/operator.md` — Specify, Build & Test, Review & Deliver, Build → Review → Archive, and the requirement-level independent check — SHALL carry in its goal condition itself a second outcome: the agent stopped at a human stop (§1 R1; for every recipe that runs Build & Test or sends the agent back to it — Build & Test, Review & Deliver and Build → Review → Archive — also that stage's 25-turn bound) and its last message names the stop, what is still open (at the bound: the conditions still unmet and the failing evidence) and the decision the owner must make — an outcome that hands the change back and is never a pass or a delivery (the requirement-level check also ends at an actual capability block or a set execution bound, and hands the requirement back). `docs/operator_cn.md` SHALL carry the same recipes verbatim. The copyable mini-kv Build & Test goal of the concepts handbook (§5.3, both languages) SHALL carry the same second outcome and the 25-turn bound. The concepts handbook (both languages) SHALL say why: the evaluator judges only the condition it was given, so a stop listed only in the goal's body keeps the loop answering "not yet met".

#### Scenario: PR-66 each recipe's goal condition carries the human-stop outcome, and the handbook says why
- WHEN the five recipes in `docs/operator.md` and `docs/operator_cn.md`, and §4.7 and the §5.3 mini-kv goal of `docs/concepts.md` and `docs/concepts_cn.md`, are read
- THEN each recipe's goal sentence carries "OR you stopped at" a human stop with the last message naming it, what is still open and the decision the owner must make, and says that outcome hands the change (for the requirement-level check, the requirement) back and is never a pass or a delivery; every goal sentence names what is still open; every recipe bounded at 25 turns, or going back to Build & Test, names that bound in its condition; the Chinese operator guide carries the identical recipe text; both concepts editions explain that a stop listed only in the body does not end the loop; and both editions' mini-kv goal ends at the 25-turn bound or a human stop too, never a pass

### Requirement: the runbook offers a prototype walk at Ground and sends the agent to the guide before it runs one
§4 Ground SHALL say: when a requirement's sources include a runnable UI prototype meant as an acceptance basis and nothing on record walks it for this scope (a `checklist.md` registered from a walk of the same prototype version), the agent offers the owner an optional prototype walk — once per requirement, when its sources are first registered — and records the answer as a `decision` so later changes see it; an authorized walk is run, a choice already made is not asked again, and screenshots or a static design are not a runnable prototype. Before running a walk the agent reads `apriori/guides/prototype-walk.md` in full and follows it. The walk's checklist is source material; the prototype's own defects follow the owner's recorded decisions first, then the requirement sources, and only what nothing settles goes to the owner as an `## Open` item; skipping the walk skips none of P2's source checks. The runbook's header SHALL no longer claim to hold everything at runtime: it names the one guide that lives beside it and when it is read. No new stop and no machine check.

#### Scenario: PW-04 Ground carries the offer, the once-per-requirement rule and the read-before-running pointer, and the header names the guide
- WHEN §4 Ground and the runbook's header are read
- THEN Ground says when to offer a walk (a runnable prototype meant as acceptance basis, no walk on record for this scope and version), once per requirement with the answer recorded as a `decision`, that an authorized walk runs and a made choice is not asked again, that screenshots or a static design do not qualify, that the agent reads `apriori/guides/prototype-walk.md` in full before running a walk, that its checklist is source material and prototype defects follow the owner's recorded decisions, then the sources, before reaching the owner, and that skipping it skips none of P2's source checks; the header says the runbook is self-contained but for that one guide, read only when a walk runs; and P3 is byte-identical to its frozen form (RIB-10)

### Requirement: the guide states its entry, its checklist and its hard constraints, and the operator guide tells the human how to ask for a walk
`guides/prototype-walk.md` (English) SHALL open with a parameterized entry (prototype and its version, sources and their versions, scope, caps set before running, where the kept artifacts and the scratch go) and a one-sentence form a human can paste; SHALL generalize the walk's method (static analysis, a local server, runtime discovery, a state model, signatures with a stated equivalence basis, traversal, interaction and boundary coverage, path-explosion control by component class, errors, screenshots, coverage with uncovered/blocked/duplicate/injected-only paths) without naming one requirement's components; SHALL define the reconciliation checklist with its minimal fields (`ID`, `version`, `observable`, `evidence`, `scope`, `ruling`, `implementation`, `verification`) as the one progress source — `scope` saying whether the delivery must show the row (`in` / `out`) apart from `ruling` saying how (`as prototype`, `corrected — <source>`, `not built — <reason>`, `owner — <Open id>`), so a prototype defect the sources correct is an `in` row reconciled against its ruling; a screenshot a row cites kept under the archived `OUT/evidence/`; and say that a later check ticks every `in` row against the implementation while checking the assertion and run conditions behind each tick, and that a later change reuses a walk for the scope it covered at that prototype version and, with the owner's authorization, continues it for what it left uncovered, blocked or out of reach — in place while the checklist's change is in flight, and once that change is archived in a successor checklist in the current change that carries every row with its id and names its archived predecessor, which is never edited (the same for a later reconciliation filling `implementation` and `verification`); SHALL say who settles a prototype defect — the owner's recorded decisions first, then the requirement sources, only what nothing settles going to the owner; SHALL state four hard constraints (equivalence justified and injected states kept apart; caps set before running and never a coverage claim; tools optional, not apriori-cli dependencies, the prototype unmodified; isolation — made-up data, external calls blocked or avoided — and scrubbing of everything written); and SHALL say how the result is registered in Ground, including for a walk run before any change exists: it registers nothing, creates no change, gives each row awaiting the owner the ruling `owner — <its own row id>` and lists those rows by id in its report, and the change that later takes the walk up registers it and opens them as `## Open` items under the same ids. `docs/operator.md` and `docs/operator_cn.md` SHALL each carry a short paragraph telling the human when the agent offers a walk, how to ask for one, what it needs on the machine, and that its checklist authorizes nothing.

#### Scenario: PW-05 the guide carries its entry, method, checklist fields and four constraints, and both operator editions point a human at it
