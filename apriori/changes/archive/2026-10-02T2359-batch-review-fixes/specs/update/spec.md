# Delta — update (batch-review-fixes)

## MODIFIED Requirements

### Requirement: update refreshes only manifest-proven tool-owned files
`apriori update` SHALL consult `apriori/managed.json` (`{ "version": 1, "files": { "<relative path>": "sha256:<64hex>" } }`, hashes over the exact bytes the tool last wrote, never line-ending-normalized) and refresh a candidate file only when the manifest lists it AND its current content hash equals the recorded hash; after a real write the entry is updated to the new content's hash. A listed file with a differing hash is `modified` — skipped with a warning naming the file and the cure (delete it and rerun `apriori init --tools <t>`). An existing file with no entry is `unmanaged` — skipped, never written — with one exception: the prototype-walk guide, adopted when its bytes are exactly a shipped edition (its own requirement below). A listed file absent on disk is `missing` — skipped (recreating is init's job). Skip-only runs still exit 0 and name every skip. When no manifest exists (pre-manifest project), update adopts what it can prove: the runbook unconditionally (refreshed as today), each command file only if its content hash equals the current template or a known shipped generation, and the guide on the same proof as above (the package embeds every generation's sha256; a membership test over the live `templates/command.md` keeps the list honest); unproven content is `unmanaged`. The adoption pass writes the manifest. A manifest that exists but is unreadable, unparseable, missing `files`, hash-malformed, `version !== 1`, or carrying a key that is absolute, contains `..`, or is outside the allowed refresh-target set (`apriori/runbook.md`, `apriori/guides/prototype-walk.md`, `TOOLS[*].command`) SHALL make update exit nonzero naming the defect before touching any target; every write additionally requires realpath containment under the project root. `--dry-run` produces the identical report and writes nothing — the manifest included.

#### Scenario: UP-06 a foreign file at a tool path survives update
- WHEN a file exists at an unselected tool's command path with no manifest entry
- THEN update leaves it byte-identical, reports `unmanaged` with the cure hint, and exits 0

#### Scenario: UP-07 an unmodified managed file refreshes and re-hashes
- WHEN a manifest-listed command file matches its recorded hash but the package template has changed
- THEN update rewrites it from the template and the manifest entry becomes the new content's hash

#### Scenario: UP-08 a locally modified managed file is protected
- WHEN a manifest-listed file (the runbook included) differs from its recorded hash
- THEN update reports `modified` with the cure hint and leaves the file byte-identical, and `--dry-run` gives the same report while writing nothing at all

#### Scenario: UP-09 pre-manifest projects are adopted only on proof
- WHEN no manifest exists and command files variously match the current template, match a known shipped generation, or carry arbitrary content
- THEN the matching files are adopted (up-to-date / refreshed respectively), the arbitrary one is `unmanaged` and untouched, the runbook refreshes as before, the guide init wrote is adopted on its bytes, and the manifest is written covering exactly those (except under `--dry-run`)

#### Scenario: UP-10 manifest hygiene fails closed
- WHEN `apriori/managed.json` is invalid JSON, lacks `files`, carries a malformed hash or `version: 2`, or lists an absolute, `..`-containing, or non-refresh-target path
- THEN update exits nonzero naming the manifest defect and no managed target is touched, identically under `--dry-run`

#### Scenario: UP-11 the shipped-generation list stays honest
- WHEN the live `templates/command.md` is hashed
- THEN the digest is a member of the package's embedded generation list (changing the template without appending fails the suite)

### Requirement: update installs the prototype-walk guide once and then manages it like the runbook
`apriori update` SHALL treat `apriori/guides/prototype-walk.md` by its manifest state: never installed (not listed, not present) → install it and record it, reported `created (first install)` and counted as a refresh in the summary; listed and unmodified → refreshed to the package's guide (`updated` / `up-to-date`) and re-hashed; listed and locally modified → reported `modified` and left alone; listed but missing → reported missing and left to `apriori init` (the existing cure); present but not listed → adopted only on proof: when its bytes are exactly a shipped edition of the guide (an install that failed before its record; the package lists every edition's sha256 and a test keeps the live guide in it), it is recorded — `adopted (its bytes are the shipped guide)`, or refreshed to the package's guide and recorded as `adopted and updated …` for an earlier edition; anything else there is reported `unmanaged` and left alone. The summary never says everything matches over a guide it could not refresh: a missing or obstructed one is counted as `N missing or obstructed (skipped)`. The first install is an exclusive create (as init's). A present guide is read once without following a symlink, and only when the opened file is inside the project — judged on the opened descriptor itself where the platform can locate it (`/proc/self/fd`), otherwise on its realpath right after opening, which is enough for a read that only judges — and that one read is what gets judged (its listed hash, or a shipped edition). A rewrite happens in place only when all of these hold on the newly opened descriptor: no symlink followed at the last component, the same device and inode as the read, no other hard link, and inside the project as located on the descriptor itself. A file swapped or redirected in between is reported `changed during refresh (skipped — …)`; a guide with another hard link, and any rewrite on a platform that cannot locate an opened descriptor (no `/proc`: macOS, Windows), is held back as `not refreshed (skipped — …)` naming the delete-and-`init` cure — fail closed, never a pathname check standing in for the descriptor. Nothing held back is recorded, and `--dry-run` predicts the same outcome. It never writes through a path that is not a regular file or that resolves outside the project, and `--dry-run` reports without writing. A CLI from before this change refuses a manifest that lists the guide (`not a refresh target`) — downgrading is not supported, and MIGRATING says so.

#### Scenario: PW-02 the guide is installed once, then refreshed, protected or left alone by its manifest state
- WHEN `apriori update` runs on a project an older CLI initialized (no guide, no entry), runs again, runs after the package's guide changed, runs after the user edited the guide, runs after the user deleted the listed guide, runs where an unlisted user file sits at the guide's path, runs again after a run that threw after installing the guide (a listed command path was a directory), runs where an unlisted earlier shipped edition sits at the path (dry-run, then for real), runs where a symlink to an outside file is swapped in for the guide between its read and its rewrite (an earlier edition being adopted, and a listed guide being refreshed), runs where `apriori/guides` is swapped for a symlink to an outside directory — holding a `prototype-walk.md` with recognized bytes — between the obstruction check and the read, runs where that directory is redirected around each open and restored right after (with the descriptor locatable, and without), runs on a platform that cannot locate a descriptor where a listed guide needs a rewrite (dry-run, then for real) or is up-to-date, runs where the listed guide has another hard link, runs from the CLI on a fresh project whose guide was deleted or replaced by a directory, and runs with `--dry-run` on a project without the guide
- THEN the first run creates the guide byte-identical to the package's, records it and reports `created (first install)` with the summary counting it; the second reports `up-to-date`; the changed package guide is `updated`, its new bytes installed and re-hashed; the edited guide is reported `modified` and keeps its bytes and its entry; the deleted one is reported missing and not recreated; the unlisted file is reported `unmanaged` and untouched; after the failed run the guide is `adopted (its bytes are the shipped guide)` and recorded, then `up-to-date`; the earlier edition is `adopted and updated` — the dry run writing nothing, the real run installing the package's guide and recording it; the swapped-in symlink is reported `changed during refresh`, its target untouched and the manifest unchanged, in both cases; the swapped parent likewise — the outside file is neither adopted nor overwritten; redirected-and-restored opens are refused at the read (descriptor located) or held back `not refreshed` at the rewrite (not located), the outside file keeping its bytes and nothing adopted; without descriptor location the guide needing a rewrite is `not refreshed` in the dry run and the real run alike, bytes and entry unchanged, an up-to-date one is `up-to-date`, and deleting it and rerunning `apriori init` records a fresh guide; the hard-linked guide is `not refreshed` in both runs and its other name keeps its bytes; the package's edition list carries the live guide and both editions shipped before it; the CLI summary for the deleted or obstructed guide says `1 missing or obstructed (skipped)` and never "everything already matches"; the dry run reports the creation and writes neither the guide nor the manifest

## Notes

Batch review (10-02, c290842) guide-2: an update (or init) that failed after writing the guide left it unrecorded, and ordinary reruns kept calling it `unmanaged`; update now adopts an unrecorded guide on the same kind of proof command files get — its exact bytes are a shipped edition (`GUIDE_GENERATIONS`). update does not write the manifest early: in a pre-manifest project that would cost a later-failing run's command files their adoption, and the adoption covers the guide anyway. Review round 1 (BRF-R1): adoption hashed the path and then rewrote it through an ordinary open, so a symlink swapped in between could redirect the write; the guide is now judged and rewritten through one no-follow read and an identity-checked no-follow write (a listed guide's refresh too, which had the same gap). Review round 2 (BRF-R4): O_NOFOLLOW guards only the last component, so a parent swapped after the obstruction check could still lead both opens to an existing outside file; containment is now judged on each opened descriptor. Round 3 (BRF-R4, rest): the realpath fallback for an unlocatable descriptor checked the pathname, not the opened file, so redirect-and-restore around each open still reached an outside file; a rewrite now fails closed where the descriptor cannot be located, and a guide with another hard link is not rewritten in place either (that would reach the other name). The cost, stated: on macOS and Windows `update` never rewrites the guide in place — an outdated one is reported `not refreshed` with the delete-and-`init` cure. guide-3: the summary counts missing and obstructed tool-owned paths. SST-4: PW-02 checks the refreshed bytes. The manifest requirement's refresh-target list now names the guide, as the code has since prototype-walk-guide. All scenario ids are kept.
