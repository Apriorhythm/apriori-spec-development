# Delta — text (fence-tilde-readers)

## ADDED Requirements

### Requirement: one fence grammar for every structural reader
`lib/text.js` SHALL define the one fence grammar every structural reader of Markdown uses — this tool's own grammar, not CommonMark (lists, blockquotes and other containers are not modeled). Backticks keep the historical reading byte for byte: a run of three backticks anywhere opens and the next run of three closes, and an unclosed opener is ordinary text. Tildes open only as a line whose first non-blank characters (up to three spaces in) are three or more `~`, an info string allowed after them, and close at the first later line holding only `~` at least as many (up to three spaces in, trailing blanks allowed); an inline `~~~` is ordinary text. Whichever opens first wins, and inside a fence the other marker is content; CRLF lines read as LF lines. Span readers (`stripFences`, `fenceSpans`) treat an unclosed tilde opener as ordinary text, as they do a backtick one; line readers use the same open and close rule (`fenceOpen`, `fenceCloses`) and keep their own policy for an unterminated fence. The readers SHALL be: scenario discovery in `check` and in `verify` (one scanner, so they agree), the delta parser in `archive`, requirement-block boundaries in a store wherever they are read — the merge, the render, the MODIFIED baselines, the single-file form and the change-scope scan — walked exactly as the historical requirement regex walked them (a heading's name may run onto its next line; a block ends at the first later line-start `### Requirement:`), except that a heading inside a fence of either marker is block content, the block keeping its raw text; and the render keeps a store's text before its first live requirement — all of it when the store has none yet — and must read back as exactly its merged blocks, in order: when a part's text would swallow another (an unclosed fence opener in a kept preamble or an earlier block pairing with a fence further on), `archive` refuses that module in both forms, naming the first block that went missing, and writes nothing — the MODIFIED-block comparison engine, the process-config reader, gate's truth-doc `source-commit` reader (C6), and the review reader — verdict lines of a self-contained review document, and the round summary's opening ids and re-review conclusions. Existing Markdown that uses only backtick fences SHALL strip exactly as before, and every spec store and delta in this repository SHALL split into the same requirement blocks as before. The scan SHALL stay near-linear on any input: no position is searched again for a backtick run once passed, and an unclosed opener never rescans or refilters the rest of the text. Outside this grammar, by design: the state-file reader (`lib/flow.js`, which already reads tildes) and the golden-path script's Quickstart shell-block extraction (`scripts/golden-path.mjs`, which reads one known README).

#### Scenario: TX-01 the shared fence grammar: tildes by line, marker and length; backticks as always
- WHEN `stripFences`, `fenceSpans`, `fenceOpen` and `fenceCloses` read tilde fences with and without info strings, longer and indented closers, shorter or tagged or other-marker lines inside, inline `~~~`, a four-space-indented run, unclosed openers of either marker, one marker's fence holding the other's, and CRLF lines
- THEN a tilde fence is removed from its opener line through its closer line; a shorter, tagged or other-marker line does not close it; inline and four-space runs are text; an unclosed opener of either marker is text; the first opener wins and the other marker inside is content; CRLF reads as LF; the spans are exactly what is removed, in order; and the line rule opens a backtick fence at any indentation and closes it on any line led by three backticks, while a tilde fence opens up to three spaces in and closes only on a bare run at least as long

#### Scenario: TX-02 the backtick reading is unchanged across this repository
- WHEN every Markdown file in the repository (more than two hundred: specs, archived bundles, reviews, docs) and synthetic backtick edges (an inline span, a longer run, an odd run) are read; every spec store and delta among them is split into requirement blocks; unfenced edge headings (a name on the next line, a nameless heading line, adjacent blocks, CRLF) are split; and hundreds of thousands of unmatched openers, long openers over short bare runs, hundreds of distinct opener lengths over a third of a million bare runs, and an unclosed backtick before a hundred thousand tilde openers are scanned
- THEN `stripFences` returns exactly what the historical lazy backtick-span regex returned for every one of them; each store, delta and edge case splits into exactly the blocks the historical requirement regex produced; and each pathological scan finishes in under two seconds

#### Scenario: TX-03 every structural reader honours the same fences
- WHEN a process-config holds a tilde-fenced `| cas | optional |` beside a live row, an unterminated tilde fence, and a longer tilde fence a shorter run does not close; a spec holds a tilde-fenced `#### Scenario:` example; a delta holds a tilde fence of heading-shaped lines inside an ADDED block (LF and CRLF); a store requirement holds a tilde-fenced requirement and scenario heading that a MODIFIED replacement rewords; a self-contained review doc quotes `VERDICT: ESCALATE` inside a tilde fence above its real verdict; and a re-review summary quotes a conclusion line inside a tilde fence
- THEN the fenced config rows grant nothing (the live row decides; the unterminated fence makes the rest inert); `check` and `verify` both pass over the fenced scenario example and bind only the real one; the delta parses with no problem, one requirement, and the fenced lines kept in its body; the store scan — on the raw store as on the stripped one — sees one requirement whose block is the raw text, fence and all; a prose-only MODIFIED replacement merged and rendered leaves no ghost block, lists the real scenario once, and is a no-op when rerun; a store holding only a fenced example, or only prose, keeps all of its text when its first requirement is ADDED (and an empty store renders just the block), each a no-op when rerun; a store whose preamble holds an unclosed tilde opener, given an ADDED requirement whose body holds a tilde fence, is refused — the readback names the swallowed requirement, the single-file form exits 1 with `FAILED PREFLIGHT — nothing written` and leaves the store byte-identical, the high-level projection reports it as a conflict and renders nothing over the store — while every store in this repository renders and reads back as its own blocks; the engine drops nothing, retaining the real scenario and reporting the reworded fenced line as missing prose; the review reads only the real verdict with no problem, and only the unfenced conclusion counts (gate C6's fenced example is GT-20's, whose test carries the tilde case too)

## Notes

Follow-up FU-1 of batch-review-fixes (registered there): the shared readers saw only backtick fences, so a tilde-fenced example in a spec, delta, config, truth doc or self-contained review was read as structure. The grammar is declared as the tool's own on purpose — CK-11's line-based CommonMark subset kept missing container edges until the owner had it read the runbook header literally (batch-recheck-fixes); readers here need agreement and the tilde marker, not CommonMark conformance. `flow.js` already read tildes for the state file and is unchanged. Review round 1: the store's requirement boundaries were read from raw text without any fence (FTR-1 — for backtick fences too, before this change), and an unclosed tilde opener rescanned the rest of the text (FTR-2); both fixed, with the corpus split guard and a performance bound in TX-02. Round 2: the backtick search was still repeated per iteration and the closer index refiltered per length (FTR-2, now a cached search and a max segment tree), the boundary walk had stopped following the regex's own consumption of a multi-line heading (FTR-3, now the regex's walk), and a store with no live requirement lost its text when one was added (FTR-4 — historically so for a prose-only store too; now kept). Round 3: keeping that text let an unclosed opener in it swallow the added block (FTR-5); the rendered store is now read back against its merged blocks and the module refused when they differ — a check that also covers any other composition of parts, backtick fences included.
