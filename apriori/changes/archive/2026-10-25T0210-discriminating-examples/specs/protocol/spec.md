# Delta — protocol (discriminating-examples)

## ADDED Requirements

### Requirement: examples discriminate, evidence asserts completely, and a fix at one entry point is not the rule's closure
The runbook SHALL say, in §4 Specify's minimal-contract rule, that a scenario's examples cover the conditions in the sources that change the expected result within that scenario's outcome category (a condition that changes the category is its own scenario, with its own representatives) and the entry points through which the same rule can fail — an entry point named as a caller reaches it (a route, a page, a command, an input channel), never as an internal handler — chosen as representatives that tell a correct implementation from a likely wrong one, never every combination by default (the sources or the owner may ask for more) — each naming the entry point it applies to and the expected result it stands for. It SHALL say, in §4 Build & Test's first action, that each chosen example has evidence that asserts, completely, the expected result it names and that a shared parametrized test counts as covering an example only when it actually executes and asserts that example's condition and entry point, while the existing rule that one parametrized test may cover a whole examples table stays. It SHALL say, in §4 Review & Deliver's disposition rule, that when a review or a test finds a rule broken at one entry point, after the fix the other entry points the same rule applies to are checked for the same omission — a finding fixed at one entry point is not closed for the rule, and a `fixed` disposition's evidence names the other entry points of that rule it checked (or says there are none). P2 SHALL carry the three clauses to the producer, and the concepts handbook SHALL echo the evidence clause in both editions. No gate, state-file field, coverage ledger, exhaustive-matrix obligation or task-specific list is added, and P3 is unchanged.

- THEN the Specify rule names the conditions that change the expected result within the scenario's outcome category (a category change being its own scenario), the entry points through which the same rule can fail named as a caller reaches them and never as an internal handler, the choice of representatives that tell a correct implementation from a likely wrong one, "never every combination by default", and the entry point and the expected result it stands for per example; the Build & Test action keeps "examples table may share ONE parametrized test" and adds that each chosen example has evidence asserting, completely, the expected result it names and that a shared test covers an example only when it actually executes and asserts that example's condition and entry point; the disposition rule keeps "scope is judged per finding, never by volume" and adds the check of the other entry points the same rule applies to when a review or a test finds the rule broken at one of them, a finding fixed at one entry point not being closed for the rule, with the `fixed` disposition's evidence naming the entry points checked; P2 carries the examples clause, the complete-assertion clause and the same-rule check; both handbook editions say each chosen example is asserted completely; and none of these texts adds a gate, a field, a coverage ledger, a Cartesian-product obligation or a task-specific list
