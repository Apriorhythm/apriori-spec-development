# Delta — protocol (ground-writeback-trace)

## ADDED Requirements

### Requirement: a persisted structure whose meaning the change extends is shared state, and Ground traces it to the write-back
The runbook SHALL say, in §4 Ground, that a persisted structure whose meaning this change extends (a stored JSON field, a settings record, a saved document whose contents the new code will read, interpret or produce in a new way) is external shared state in the sense of Specify's three moments; that Ground traces, for each one, how it is read, what intermediate form it takes, where it is edited and how it is written back; that it records as an `observed:` line what the existing read → edit → write-back path does to the parts of the stored value the changed representation cannot hold (kept, merged, dropped or refused, for example); that until that write-back has been read, that fate is an `assumption`, with the assumption lifecycle Ground already has; and that where the change builds or replaces the write-back, that fate is contract behavior for Specify's runtime-update moment — a `decision` when a source or the owner settles it, otherwise an `## Open` item for the owner — not an assumption. P1 SHALL carry the same instruction to the producer. P2's shared-state rule and §4 Specify's minimal-contract rule SHALL name such a structure among the external shared state whose three moments are described, and SHALL say that for a structure the change extends, the runtime-update moment states what happens to the parts of the stored value the new code cannot represent. The concepts handbook (both editions) and the CLI reference's spec-authoring rules (both editions) SHALL echo the clause where they state the three-moments rule. No gate, flow-state field, diagram, search action or new document is added.

#### Scenario: PR-76 the runbook makes an extended persisted structure shared state and asks Ground to trace it to the write-back
- WHEN §4 Ground, P1, P2's shared-state rule, §4 Specify's "Minimal means minimal" rule, the concepts handbook (both editions) and the CLI reference's spec-authoring rules (both editions) are read
- THEN §4 Ground has a rule naming a persisted structure whose meaning this change extends as shared state in the sense of Specify's three moments, asking for the trace read → intermediate form → edit → write-back, for an `observed:` line on what the existing write-back does to the parts the changed representation cannot hold (kept, merged, dropped or refused, for example), stating that until that write-back is read that fate is an `assumption`, and routing the fate of a write-back the change builds or replaces to Specify's runtime-update moment as a `decision` or an `## Open` item, never an assumption; P1 says the same to the producer; P2's shared-state rule and §4 Specify's rule include "a stored structure whose meaning you extend / this change extends" among the external shared state and say the runtime-update moment states the fate of the parts the new code cannot represent (what the changed page or API cannot show or edit); the concepts handbook and the CLI reference echo the clause in both editions where they state the three-moments rule; and none of these texts adds a gate, a flow-state field, a diagram, a search action or a new document
