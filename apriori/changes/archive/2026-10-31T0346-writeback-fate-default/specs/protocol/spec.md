# Delta — protocol (writeback-fate-default)

## ADDED Requirements

### Requirement: what an edit path cannot represent is kept or refused by default, never dropped silently, and the walk of that path is evidence
The runbook SHALL say, in §4 Ground's rule on a persisted structure whose meaning the change extends, that the fate of the parts of the stored value the changed representation cannot hold is contract behavior (not an assumption) whenever this change changes how the stored content enters an edit path, how it is represented, edited or written back — an existing adapter or representation the change extends included, whether or not the write-back function itself is touched; that Specify's runtime-update moment states that fate as a `decision` when a source or the owner settles it, and otherwise as the runbook's safe default recorded as a decision citing the rule — never as an `## Open` item asking the owner whether stored data may be lost; and that the safe default is: without a source that authorizes the loss, no part of a stored value is dropped because the changed page or API cannot represent it ("the existing path already drops it" states the current behavior and authorizes nothing) — where the stored structure and its meaning can be kept, the write-back keeps the parts the edit did not touch and applies the edit (a mechanical splice that changes what the stored value means is not keeping it); where that cannot be made reliable, the edit is refused, or that region is read-only, before anything destructive happens, with the reason shown, and the stored value re-reads unchanged; a source that requires the object to be editable is not satisfied by read-only (a conflict to settle like any other); what the owner may want beyond the safe default is a follow-up. P1 SHALL carry the same trigger and the same default to the producer. §4 Specify's minimal-contract rule and P2's shared-state rule SHALL say that, where no source settles it, the runtime-update moment states the safe default as a decision citing §4 Ground. §4 Build & Test's "run the tests the risks call for" rule and P2's Build & Test part SHALL say that for a stored structure the change extends the evidence includes one full walk with stored content the changed page or API cannot represent — read the stored object → attempt the edit → save, or the refusal → re-read it independently — showing the untouched parts still there with their meaning (for a refusal: the message, and the stored value unchanged), and that the adapter's conversion alone, a success status from the API alone, or a page refresh alone is not that evidence. The concepts handbook (both editions) and the CLI reference's spec-authoring rules (both editions) SHALL echo the default where they echo the runtime-update clause. No gate, flow-state field, diagram, search action, new document or task-specific text is added, and P3 is unchanged.
