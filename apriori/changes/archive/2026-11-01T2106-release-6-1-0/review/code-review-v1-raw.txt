 # Changelog
 
+## 6.1.0 — 2026-11-01 · stamped process records, and tighter rules for runtime evidence, stored structures and source outcomes
+
+**What this version is.** The v6-dev line as of this entry: 6.0.0 plus the seven changes below, filed
+here as subsections (they were written as `Unreleased since 6.0.0` entries while the line was built).
+Six of them change only the runbook's rules; `gates-note-command` adds the `apriori note` command and
+an `advisories` field to `status --json`. Nothing is removed and no flag, delta format or flow-state
+field changes meaning, so a project needs no migration — `apriori update` refreshes its runbook copy
+(MIGRATING.md). Consumers that validate `status --json` fields strictly need to accept `advisories`.
+
+**Evidence, stated as it stands.** 6.1.0 adds a time-stamped process-record command and tightens the
+rules for runtime evidence, write-back to stored structures, and changes to source commitments. On the
+established B4 path of the custom-properties benchmark, the last five runs all kept the stored value or
+refused safely, while the four runs before them all overwrote it; that comes from non-concurrent,
+small-sample observations and is not a general guarantee of zero data loss. In the same worklog
+source-conflict scenario, a fixed-input replay and a controlled experiment both showed the producer
+keeping the source's result and leaving the conflict to the owner. Higher overall correctness, an
+advantage over working without apriori, and cost improvements are not shown. (Benchmark records:
+`evaluate-projects` comparisons `ref-d5a5060-`, `ref-c6543e7-`, `ref-0b32a90-*`,
+`probe-0b32a90-review-replay-1`, `exp-r1101-source-review`.)
+
+**Release steps (2026-11-01).** Tag `v6.1.0` is cut on this line; `main` and `release/v6` are
+fast-forwarded to it; the package is published to npm as `apriori-cli@6.1.0`.

+### preserve-source-outcomes (2026-10-31) — the source's outcome is not reduced when it becomes an expected result or when a review suggests otherwise
+
+**Specify / P2.** For the examples that carry an observed source-vs-current conflict, return to the source itself: cite the applicable clause and state each required observable result separately, preserving its conditions and alternatives; equivalent wording is sufficient, but a consequence that can also hold when a required result is absent is not, and the expected result must exclude the conflicting outcome observed in current behavior. This replaces the sentence "each expected result retains every source obligation applicable to that example" (PR-78), which both producers of the trigger run believed they had satisfied while their tests accepted the wrong outcome outright. **Review & Deliver / P2 Build & Test.** Before accepting a suggested fix that changes an observable result a source states, the disposition cites the source clause and states the difference; current behavior, convention or a review recommendation alone does not authorize the change, the contract is not rewritten to make it a fix, the source's result is retained unless a source or a recorded owner decision authorizes otherwise, and an independently supported constraint that prevents that is recorded with both bases and left pending the owner — not a non-blocking follow-up. P1 and P3 are unchanged (guard compares both by hash). PR-79; Claude × Astra consensus R1031B, human 2026-10-31.

+### source-conflict-entry-points (2026-10-31) — a source constraint applies to the existing entry points too
+
+Ground: where a source explicitly rules out an exception, override or continuation of behavior under a stated condition ("does not override", "regardless of", "no longer"), Ground checks how the existing or reused paths handle that condition — within the change's requirement scope (the behavior being delivered, the caller-visible entry points the sources name or imply and the code they reuse; not the files being changed) — tracing each affected entry point far enough to establish what determines its observable result and recording condition, entry point, deciding code and current result as `observed:` lines; the same trace for any source-vs-current-behavior conflict Ground has already observed; only the paths needed, never a repository sweep; checking only new code does not settle the existing entry points the same requirement governs. Specify / P2: every observed conflict reaches the examples at the affected caller-visible entry points, existing ones included, one representative per distinct deciding path (shared only on `observed:` evidence that the same path decides under that condition), each expected result keeping every applicable source obligation. P1 carries the trace. Trigger: v6-dev@d5a5060 on custom-properties@3 twice — both producers had observed the existing permission shortcuts the task ruled out, one wrote "new endpoints need a strict check", and the examples covered only the new entry points (Claude × Astra consensus R1031, human 2026-10-31). P3, §4 Build & Test and the docs are unchanged; no new mechanism. Guard: `test/source-conflict-entry-points.test.js` (asserts the wording, compares P3 with its v6-dev@d5a5060 text by hash, and forbids task-specific words).

+### writeback-fate-default (2026-10-31) — what the edit path cannot represent is kept or refused, never dropped silently
+
+Ground / Specify: the fate of the parts of a stored value the changed page or API cannot represent is contract behavior whenever the change changes how that content enters an edit path, is represented, edited or written back — an existing adapter the change extends included, whether or not the write-back function itself is touched (the "builds or replaces the write-back" trigger of ground-writeback-trace was too narrow: a producer that only extended an adapter kept "the previous behavior" — dropping — by its own decision). Where no source settles it, the runtime-update moment states the runbook's safe default as a decision citing §4 Ground, never an `## Open` item asking the owner whether data may be lost: without a source authorizing the loss nothing is dropped silently ("the existing path already drops it" authorizes nothing) — keep what the edit did not touch and apply the edit where structure and meaning can be kept (a meaning-changing splice is not keeping), otherwise refuse the edit or make the region read-only before anything destructive happens, with the reason shown and the stored value re-reading unchanged; read-only does not satisfy a source that requires editability; the owner's wishes beyond the default are a follow-up. Build & Test / P2: for such a structure the evidence includes one full walk with content the edit path cannot represent — read → attempt the edit → save or the refusal → independent re-read — showing the untouched parts kept with their meaning (refusal: message shown, stored value unchanged); the adapter's conversion, a success status or a refresh alone is not that evidence. P1 carries trigger and default; concepts and the CLI reference echo the default in both editions (PR-77). Trigger: v6-dev@0cdebfc still failed custom-properties B4 twice (2026-10-30); Claude × Astra consensus R1030 §二. No gate, field, diagram, search action or task-specific text is added; P3 is unchanged.
+
+### ground-writeback-trace (2026-10-28) — an extended persisted structure is shared state, traced to the write-back
+
+Ground: a persisted structure whose meaning the change extends (a stored JSON field, a settings record, a saved document) is external shared state in the sense of Specify's three moments; Ground traces how it is read, what intermediate form it takes, where it is edited and how it is written back, and records as `observed:` what the existing write-back does to the parts of the stored value the changed representation cannot hold (kept, merged, dropped or refused, for example) — until that write-back is read, that fate is an `assumption`; where the change builds or replaces the write-back, that fate is contract behavior for Specify's runtime-update moment (a `decision` or an `## Open` item), never an assumption. P1 carries the instruction; P2 and §4 Specify name such a structure among the shared state and pin the runtime-update moment to that fate; concepts and the CLI reference echo it in both editions (PR-76). Trigger: the candidate v6-dev@e8f9342 still failed custom-properties B4 twice (2026-10-28) — Ground had found the stored field and the editor's adapter but never asked what the write-back does to the conditions the editor cannot show. No gate, field, diagram or search action is added.
+
+### discriminating-examples (2026-10-25) — examples that tell right from wrong, asserted completely, at every entry point
+
+Specify: a scenario's examples cover the conditions in the sources that change the expected result and the entry points in the real code through which the same rule can fail — representatives that tell a correct implementation from a likely wrong one, never every combination by default — each naming its entry point and expected result. Build & Test: each chosen example has evidence that asserts its complete expected result; a shared parametrized test counts as covering an example only when it actually executes and asserts that example's condition and entry point. Review & Deliver: after a fix, the other entry points the same rule applies to are checked for the same omission — a finding fixed at one entry point is not closed for the rule. P2 carries all three; the concepts handbook (both editions) echoes the evidence clause. No gate, field, coverage ledger or matrix obligation is added; P3 is untouched. Why: across four evaluation-baseline runs the failing requirements were in the contract but not carried to every entry point (a role rule enforced in the API, not in the settings page or the detail editor; a decoding guard on the query parameter, not on the body) and the tests asserted less than the contract (`"a" * 256` cannot tell code points from UTF-16 units; a creator's detail read asserted a field's absence instead of 403/404) — Claude × Astra consensus 2026-10-25 (R1024 §六). Specs: protocol (PR-75).
+
+### runtime-evidence-not-reviewable (2026-10-24) — review reads, it does not run
+
+The Build & Test sentence "Where no executable instrument exists for a risk, the independent review is the instrument there" is replaced: a runtime behavior no test executes — a new or changed page or user-visible flow, a migration, a job, a real-service call — is run once in the environment at hand and recorded as an `observed:` line (done / expected / happened / where the evidence lives), or it is an `## Open` item for the owner, never only a sentence in the final report; "no test runner" is not "cannot be run"; a run of the normal path is evidence for that path only; the independent review confirms what reading settles and never closes a runtime gap. P2 carries the clause with its condition (the run first; `## Open` only for a run that genuinely cannot be made); the concepts handbook and VISION (both editions) agree, and the old project-type exemption list is gone. No gate, field or UI-specific check is added, UNBOUND stays advisory, and a change that has its evidence or can get it adds no owner stop. Why: in three evaluation-baseline runs of 6.0.0 every producer wrote "the UI was never run in a browser" into its final report under the old sentence, and the one new front-end defect of those runs was missed that way (Claude × Astra consensus 2026-10-24, ①A). Specs: protocol (PR-74).
+
+### gates-note-command (2026-10-24) — the CLI stamps `gates:` entries
+
+`apriori note --change <name> [--owner] "<text>"` appends one entry to a change's `gates:` log with the CLI's local clock as its stamp — the time of recording, never a time the agent fills in; there is no date argument. It only appends, refuses anything but an active change's own flow-state with one `gates:` block, and writes a multi-line text as one entry. `apriori status --change` now flags a stamp later than the machine's clock as an `advisory:` line and `advisories` in `--json` — advisory only: stamps carry no time zone, so no gate, archive refusal or decision reading changes. RUNBOOK §3 and §1 R4 and the C8 hints send the agent to the command; `docs/cli.md` / `docs/cli_cn.md` document it. Why: in three evaluation-baseline runs of 6.0.0 every hand-written gates stamp but the scaffold's disagreed with the real production time (Claude × Astra consensus 2026-10-24). Specs: note (NT-01..NT-06, new), status (ST-47, ST-48), protocol (PR-73).

./docs/cli.md:87:**Review rounds and escalation.** `--change` adds two derived fields — nothing here is read off a hand-written `round:`. `review.families` carries one entry **per review family** (`spec-review`, `code-review`, …): `{family, round, verdict, issuesOpen, stopped, escalating}`. function exitWhenDrained(code) {

// A canonical entry is a fence-outside header blockquote `> `runbook-version: X.Y``;
// body-text or fenced occurrences are never matched. RUNBOOK.md is the one runbook (English only).
function checkRunbookVersion(root, files) {
  const fails = [];
  let pkgVer;                           // 'X.Y' of the package version (a pre-release tag is ignored)
  try {
    const m = /^(\d+)\.(\d+)/.exec(String(JSON.parse(fs.readFileSync(path.join(root, 'package.json'), 'utf8')).version || ''));
    pkgVer = m ? `${m[1]}.${m[2]}` : '';
  } catch { return fails; }             // no readable package.json → not this check's business
  if (!pkgVer) return fails;
  for (const label of ['RUNBOOK.md']) {
    const text = files[label];
    if (text === undefined) {           // the runbook is REQUIRED under --self
      fails.push(`CK-11 ${label}: the canonical runbook is missing — a version header is required`);
      continue;
    }
    // header region only: before the first h2 — a body-text blockquote never counts. It is read
    // LITERALLY, never as CommonMark (owner 2026-10-03, batch-recheck-fixes): a run of three or more
    // backticks or tildes anywhere in it — whatever its indentation, container or purpose — is an
    // unsupported header format, so no fence is ever read, and so none can be misread
    const h2 = text.search(/^##\s/m);
    const header = h2 >= 0 ? text.slice(0, h2) : text;
    const fenceRun = /`{3,}|~{3,}/.exec(header);
    if (fenceRun) {
      fails.push(`CK-11 ${label}: unsupported header format — line ${lineOf(header, fenceRun.index)} has a run of three or more backticks or tildes; the header region (before the first h2) is read literally and carries no code fence, so no runbook-version entry is read`);
      continue;
    }
    const hits = [...header.matchAll(/^>\s*`runbook-version:\s*([^`]*)`/gm)];
    if (hits.length === 0) fails.push(`CK-11 ${label}: no \`runbook-version\` blockquote entry (expected \`> \`runbook-version: ${pkgVer}\`\`)`);
    else if (hits.length > 1) fails.push(`CK-11 ${label}: ${hits.length} runbook-version entries — exactly one required`);
    else {
      const m = /^(\d+)\.(\d+)$/.exec(hits[0][1].trim());
      if (!m) fails.push(`CK-11 ${label}: malformed runbook-version value '${hits[0][1].trim()}' (expected X.Y)`);
      else if (`${m[1]}.${m[2]}` !== pkgVer) fails.push(`CK-11 ${label}: runbook-version ${m[1]}.${m[2]} != package ${pkgVer} (major.minor must match)`);
    }
  }
  return fails;
}

// npm is a .cmd shim on Windows: spawning the bare name fails with ENOENT, and Node refuses to spawn a
// .cmd without a shell (CVE-2024-27980). Every test that packs the package goes through this seam, so
// the Windows CI matrix runs it the same way the POSIX one does. On the shell path an argument with
// whitespace is quoted (a temp dir under a user name with a space); the tests pass nothing else.
const { spawnSync, execFileSync } = require('node:child_process');
const WIN = process.platform === 'win32';
const NPM = WIN ? 'npm.cmd' : 'npm';
const shellArgs = (args) => (WIN ? args.map((a) => (/\s/.test(a) ? `"${a}"` : a)) : args);
function npmSync(args, opts = {}) { return spawnSync(NPM, shellArgs(args), { ...opts, shell: WIN }); }
function npmOut(args, opts = {}) { return execFileSync(NPM, shellArgs(args), { ...opts, shell: WIN }); }
module.exports = { npmSync, npmOut, NPM };
