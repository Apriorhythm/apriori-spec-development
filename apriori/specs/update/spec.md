### Requirement: apriori update refreshes tool-owned files after a CLI upgrade
`apriori update` SHALL refresh every tool-owned scaffolded file — the runbook copy (`apriori/runbook.md`) and per-tool command files that already exist — to the installed package's versions, SHALL never modify user-owned files and never create new per-tool files (the only creations permitted are protocol-required scaffolding, UP-05, and the prototype-walk guide's first install, PW-02), and SHALL report per-file what it did.

#### Scenario: UP-01 refreshes the runbook copy and existing command files
- WHEN `apriori update` runs in an initialized project whose `apriori/runbook.md` or existing per-tool command files differ from the installed package's copies
- THEN each differing file is rewritten to the packaged version and reported `updated`; identical files are reported `up-to-date`; exit 0

#### Scenario: UP-02 user-owned files are never touched
- WHEN `apriori update` runs
- THEN `apriori/process-config.md`, `specs/`, `changes/`, `review/`, `truth/`, and the tool rules files the init pointer was appended to (CLAUDE.md, AGENTS.md, …) are left byte-identical, and no new per-tool file is created (adding a tool is `apriori init`'s job); the only creations permitted are protocol-required scaffolding (UP-05) and the prototype-walk guide's first install (PW-02)

#### Scenario: UP-03 uninitialized project errors
- WHEN `apriori update` runs where `apriori/runbook.md` does not exist
- THEN it errors with a message naming `apriori init` and exits non-zero

#### Scenario: UP-04 --dry-run previews without writing
- WHEN `apriori update --dry-run` runs with stale files present
- THEN it reports what would be refreshed and writes nothing

#### Scenario: UP-05 protocol-required scaffolding is re-established
- WHEN `apriori update` runs in a project initialized before the gitignored scratch dir existed (no `apriori/.gitignore`)
- THEN it creates `apriori/.gitignore` (containing `tmp/`) and `apriori/tmp/`, so the refreshed runbook's "gitignored `apriori/tmp/`" claim holds; an existing `.gitignore` is never modified

### Requirement: update refreshes only manifest-proven tool-owned files
`apriori update` SHALL consult `apriori/managed.json` (`{ "version": 1, "files": { "<relative path>": "sha256:<64hex>" } }`, hashes over the exact bytes the tool last wrote, never line-ending-normalized) and refresh a candidate file only when the manifest lists it AND its current content hash equals the recorded hash; after a real write the entry is updated to the new content's hash. A listed file with a differing hash is `modified` — skipped with a warning naming the file and the cure (delete it and rerun `apriori init --tools <t>`). An existing file with no entry is `unmanaged` — skipped, never written — with one exception: the prototype-walk guide, adopted when its bytes are exactly a shipped edition, read on a descriptor the platform can locate (its own requirement below). A listed file absent on disk is `missing` — skipped (recreating is init's job). Skip-only runs still exit 0 and name every skip. When no manifest exists (pre-manifest project), update adopts what it can prove: the runbook unconditionally (refreshed as today), each command file only if its content hash equals the current template or a known shipped generation, and the guide on the same proof as above (the package embeds every generation's sha256; a membership test over the live `templates/command.md` keeps the list honest); unproven content is `unmanaged`. The same adoption pass runs once more for a manifest marked `"adoptPending": true` (a project init touched mid-migration, see init): unlisted files are adopted on the same proof (the runbook unconditionally, command files only on a shipped generation), while listed files keep every rule above — an edited one stays `modified`. The adoption pass writes the manifest — materializing it, or rewriting it without the mark — and only at the end of a run that got through, so a run that throws leaves the mark for the next one. A manifest that exists but is unreadable, unparseable, missing `files`, hash-malformed, `version !== 1`, carrying an `adoptPending` that is not a boolean, or carrying a key that is absolute, contains `..`, or is outside the allowed refresh-target set (`apriori/runbook.md`, `apriori/guides/prototype-walk.md`, `TOOLS[*].command`) SHALL make update exit nonzero naming the defect before touching any target; every write additionally requires realpath containment under the project root. `--dry-run` produces the identical report and writes nothing — the manifest included.

#### Scenario: UP-06 a foreign file at a tool path survives update
- WHEN a file exists at an unselected tool's command path with no manifest entry
- THEN update leaves it byte-identical, reports `unmanaged` with the cure hint, and exits 0

#### Scenario: UP-07 an unmodified managed file refreshes and re-hashes
- WHEN a manifest-listed command file matches its recorded hash but the package template has changed
- THEN update rewrites it from the template and the manifest entry becomes the new content's hash

#### Scenario: UP-08 a locally modified managed file is protected
- WHEN a manifest-listed file (the runbook included) differs from its recorded hash
- THEN update reports `modified` with the cure hint and leaves the file byte-identical, and `--dry-run` gives the same report while writing nothing at all

#### Scenario: UP-09 pre-manifest projects are adopted only on proof
- WHEN no manifest exists and command files variously match the current template, match a known shipped generation, or carry arbitrary content
- THEN the matching files are adopted (up-to-date / refreshed respectively), the arbitrary one is `unmanaged` and untouched, the runbook refreshes as before, the guide init wrote is adopted on its bytes (where an opened descriptor can be located; elsewhere it is held back `not refreshed` and left out), and the manifest is written covering exactly those (except under `--dry-run`)

#### Scenario: UP-10 manifest hygiene fails closed
- WHEN `apriori/managed.json` is invalid JSON, lacks `files`, carries a malformed hash or `version: 2`, or lists an absolute, `..`-containing, or non-refresh-target path
- THEN update exits nonzero naming the manifest defect and no managed target is touched, identically under `--dry-run`

#### Scenario: UP-11 the shipped-generation list stays honest
- WHEN the live `templates/command.md` is hashed
- THEN the digest is a member of the package's embedded generation list (changing the template without appending fails the suite)

### Requirement: update warns on legacy 3.x layouts
`apriori update` SHALL run the same legacy-layout detection as doctor's D8 — the apriori-owned roots `apriori/review/`, `apriori/design/`, `apriori/explore/`, one shared list, never diverging — and print a warning naming the roots found and pointing at the MIGRATING.md 4.0 section, without blocking the update itself: refreshing the protocol while the artifacts sit in pre-4.0 roots must be loud, never silent. Top-level `requirement/` and `spike/` are outside the probe list for the reason given in the doctor spec (ordinary names, existence-level probe); update stays silent about them too.

#### Scenario: UP-12 updating a legacy-layout project is loud
- WHEN `apriori update` runs in a project still carrying `apriori/review/` and `apriori/design/`, alongside a top-level `requirement/` of the project's own
- THEN the update proceeds as normal AND a warning names the two apriori-owned roots with the migration pointer — and never names `requirement/`; a clean 4.0 project updates without the warning

### Requirement: update installs the prototype-walk guide once and then manages it like the runbook
`apriori update` SHALL treat `apriori/guides/prototype-walk.md` by its manifest state: never installed (not listed, not present) → install it and record it, reported `created (first install)` and counted as a refresh in the summary; listed and unmodified → refreshed to the package's guide (`updated` / `up-to-date`) and re-hashed; listed and locally modified → reported `modified` and left alone; listed but missing → reported missing and left to `apriori init` (the existing cure); present but not listed → adopted only on proof: when its bytes are exactly a shipped edition of the guide (an install that failed before its record; the package lists every edition's sha256 and a test keeps the live guide in it), it is recorded — `adopted (its bytes are the shipped guide)`, or refreshed to the package's guide and recorded as `adopted and updated …` for an earlier edition; anything else there is reported `unmanaged` and left alone. The summary never says everything matches over a guide it could not refresh: a missing or obstructed one is counted as `N missing or obstructed (skipped)`. The first install is an exclusive create (as init's). A present guide is read once without following a symlink, and only when the opened file is inside the project — judged on the opened descriptor itself where the platform can locate it (`/proc/self/fd`), otherwise on its realpath right after opening, which is enough for a read that only judges — and that one read is what gets judged (its listed hash, or a shipped edition). Adoption records ownership on the strength of that read, so it too needs the read located on its descriptor: where it is not, an unrecorded guide is held back `not refreshed (skipped — …)` whatever its bytes, rewrite or not. A rewrite happens in place only when all of these hold on the newly opened descriptor: no symlink followed at the last component, the same device and inode as the read, no other hard link, and inside the project as located on the descriptor itself. A file swapped or redirected in between is reported `changed during refresh (skipped — …)`; a guide with another hard link, and any rewrite on a platform that cannot locate an opened descriptor (no `/proc`: macOS, Windows), is held back as `not refreshed (skipped — …)` naming the delete-and-`init` cure — fail closed, never a pathname check standing in for the descriptor. Nothing held back is recorded, and `--dry-run` predicts the same outcome. It never writes through a path that is not a regular file or that resolves outside the project, and `--dry-run` reports without writing. A CLI from before this change refuses a manifest that lists the guide (`not a refresh target`) — downgrading is not supported, and MIGRATING says so.

#### Scenario: PW-02 the guide is installed once, then refreshed, protected or left alone by its manifest state
- WHEN `apriori update` runs on a project an older CLI initialized (no guide, no entry), runs again, runs after the package's guide changed, runs after the user edited the guide, runs after the user deleted the listed guide, runs where an unlisted user file sits at the guide's path, runs again after a run that threw after installing the guide (a listed command path was a directory), runs where an unlisted earlier shipped edition sits at the path (dry-run, then for real), runs where a symlink to an outside file is swapped in for the guide between its read and its rewrite (an earlier edition being adopted, and a listed guide being refreshed), runs where `apriori/guides` is swapped for a symlink to an outside directory — holding a `prototype-walk.md` with recognized bytes — between the obstruction check and the read, runs where that directory is redirected around each open and restored right after (with the descriptor locatable, and without), runs on a platform that cannot locate a descriptor where a listed guide needs a rewrite (dry-run, then for real) or is up-to-date, runs where the listed guide has another hard link, runs where the team's own unrecorded guide sits inside while an outside directory holds the current packaged guide and the directory is redirected around each open and restored right after (with the descriptor locatable, and without), runs from the CLI on a fresh project whose guide was deleted or replaced by a directory, and runs with `--dry-run` on a project without the guide
- THEN the first run creates the guide byte-identical to the package's, records it and reports `created (first install)` with the summary counting it; the second reports `up-to-date`; the changed package guide is `updated`, its new bytes installed and re-hashed; the edited guide is reported `modified` and keeps its bytes and its entry; the deleted one is reported missing and not recreated; the unlisted file is reported `unmanaged` and untouched; after the failed run the guide is `adopted (its bytes are the shipped guide)` and recorded, then `up-to-date`; the earlier edition is `adopted and updated` — the dry run writing nothing, the real run installing the package's guide and recording it; the swapped-in symlink is reported `changed during refresh`, its target untouched and the manifest unchanged, in both cases; the swapped parent likewise — the outside file is neither adopted nor overwritten; redirected-and-restored opens are refused at the read (descriptor located) or held back `not refreshed` at the rewrite (not located), the outside file keeping its bytes and nothing adopted; without descriptor location the guide needing a rewrite is `not refreshed` in the dry run and the real run alike, bytes and entry unchanged, an up-to-date one is `up-to-date`, and deleting it and rerunning `apriori init` records a fresh guide; the hard-linked guide is `not refreshed` in both runs and its other name keeps its bytes; the outside current guide is never adopted for the team's guide — refused at the read (located) or held back `not refreshed` (not located), the team's bytes untouched and no entry recorded; and on a platform that cannot locate a descriptor at all, every rewrite or adoption in this sequence is `not refreshed` with bytes and entries unchanged, and the suite asserts exactly that there; the package's edition list carries the live guide and both editions shipped before it; the CLI summary for the deleted or obstructed guide says `1 missing or obstructed (skipped)` and never "everything already matches"; the dry run reports the creation and writes neither the guide nor the manifest
