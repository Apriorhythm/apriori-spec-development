# LAB-NOTES.md — friction log (experiment overlay, not part of the OpenSpec process)

- explore.md step "Check for context" says to run `openspec list --json` unconditionally, but on a brand-new project (no `openspec/` dir yet) this exits 1 with a `list_error`. The command doesn't branch on "not initialized yet" vs "no active changes" — had to infer that `openspec init` comes later (at propose time) rather than during explore.
- `openspec new change` worked fine without `openspec init` (auto-created openspec/changes/), yet `openspec list` had earlier insisted "Run 'openspec init' first". Inconsistent init story between commands.
- CLI flag inconsistency: `status`/`instructions` take `--change <name>`, but `validate` rejects `--change` (suggests `--changes`); positional `openspec validate <name>` is the actual form. Explore.md even lists `validate` among commands that accept `--store`, reinforcing the wrong-flag guess.
- propose.md says to re-run `openspec status --json` after each artifact and check `applyRequires` done — fine, but `status` exits 0 with JSON and initial suspicion of `status` exiting 1 was a false alarm — the exit 1 came from the chained `validate --change` failure, standalone `status` exits 0. Friction was self-inflicted by chaining; no CLI bug.
- Session interruption mid-apply: recovery via tasks.md checkboxes worked, BUT only because progress happened to be checkpointed. I had batched checkbox updates (marked 1.x-3.x together, hadn't marked 4.x though the code was done) — after resume the checkboxes claimed less progress than reality, and I had to re-verify files/tests to reconcile. apply.md's "update task checkbox immediately after completing each task" is load-bearing for crash recovery; batching is tempting and nothing enforces it.
- `openspec instructions apply` returned task IDs "1".."14" (flat sequence) while tasks.md uses "1.1".."5.3" — two numbering schemes for the same tasks; harmless but momentarily confusing when cross-referencing.
- archive.md step 4 mandates re-prompting "Sync now vs Archive without syncing" even though my previous turn already told the user archive = sync + move and they confirmed. Process forces a redundant confirmation.
- archive.md step 4 says to have a subagent invoke skill `openspec-sync-specs` — no such skill exists in this environment (only the four opsx command files were provided). If the user picks "sync", the prescribed mechanism is broken; will have to do the merge manually.
