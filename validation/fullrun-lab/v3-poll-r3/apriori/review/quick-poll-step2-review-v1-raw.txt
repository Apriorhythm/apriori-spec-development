## Requirement: 创建投票(Poll Creation)

发起人提交标题 + 2–10 选项 + 可选 mode/deadline,服务端校验后持久化并返回分享链接与私密管理链接。所有 `POST` body ≤ 16 KiB、`Content-Type: application/json`。

#### Scenario: PC-01 创建合法投票返回两条链接
- **If** `POST /api/polls` body `{title:"午饭吃啥", options:["火锅","麻辣烫"]}`(合法,mode 省略)
- **Then** 201,响应含 `shareUrl` 与 `adminUrl`;新 poll `status="open"`、`mode="single"`、各选项 `votes=0`、`totalVoters=0`;`shareUrl` 不含 admin token。

#### Scenario: PC-02 选项少于 2 个被拒
- **If** `POST /api/polls` 的 `options` 长度 < 2
- **Then** 400 `{error:"OPTION_COUNT_OUT_OF_RANGE"}`,不创建任何文件。

#### Scenario: PC-03 恰好 10 个选项创建成功
- **If** `options` 长度 = 10 且各项合法
- **Then** 201 创建成功,10 个选项全部保存。

#### Scenario: PC-04 选项多于 10 个被拒
- **If** `options` 长度 > 10
- **Then** 400 `OPTION_COUNT_OUT_OF_RANGE`,不创建。

#### Scenario: PC-05 空白标题被拒
- **If** `title` 为空串或仅空白(trim 后为空)
- **Then** 400 `TITLE_REQUIRED`。

#### Scenario: PC-06 标题超长被拒
- **If** `title` 的 Unicode code point 数 > 100
- **Then** 400 `TITLE_TOO_LONG`。

#### Scenario: PC-07 空白选项被拒
- **If** 任一 option 的 text trim 后为空
- **Then** 400 `OPTION_REQUIRED`。

#### Scenario: PC-08 选项超长被拒
- **If** 任一 option 的 code point 数 > 50
- **Then** 400 `OPTION_TOO_LONG`。

#### Scenario: PC-09 mode 缺省为 single
- **If** 创建时不传 `mode`
- **Then** poll 的 `mode` 持久化为 `"single"`。

#### Scenario: PC-10 非法 mode 被拒
- **If** `mode` 不是 `"single"` 或 `"multi"`
- **Then** 400 `INVALID_MODE`。

#### Scenario: PC-11 过去/等于当前的 deadline 被拒
- **If** 创建时 `deadline` 解析后 ≤ 当前服务器时间
- **Then** 400 `DEADLINE_IN_PAST`。

#### Scenario: PC-12 不可解析的 deadline 被拒
- **If** `deadline` 不是可解析的 ISO 8601 字符串
- **Then** 400 `INVALID_DEADLINE`。

#### Scenario: PC-13 malformed JSON 被拒
- **If** `POST /api/polls` 的 body 不是合法 JSON
- **Then** 400 `INVALID_JSON`,不创建。

#### Scenario: PC-14 字段缺失/类型错误被拒
- **If** `title` 非 string、或 `options` 非数组等类型不符
- **Then** 400 `INVALID_PAYLOAD`。

#### Scenario: PC-15 请求体超过 16 KiB 被拒
- **If** `POST` body 字节数 > 16384
- **Then** 413 `PAYLOAD_TOO_LARGE`,不创建。

## Requirement: 投票(Voting)

投票人经分享链接对指定选项 id 提交投票;服务端串行计票并原子落盘,返回结果快照。

#### Scenario: VT-01 单选投票计票
- **If** single poll,`POST /api/polls/<id>/vote` body `{optionIds:["<opt>"]}`
- **Then** 200,该选项 `votes+1`、`totalVoters+1`,响应含各选项票数与总人数。

#### Scenario: VT-02 单选投多项被拒
- **If** single poll 且 `optionIds` 长度 > 1
- **Then** 400 `SINGLE_CHOICE_VIOLATION`,不计票。

#### Scenario: VT-03 多选投多项计票
- **If** multi poll,`optionIds` 含多个不同合法选项
- **Then** 200,所选各项各 `+1`,`totalVoters` 只 `+1`。

#### Scenario: VT-04 空选择被拒
- **If** `optionIds` 为空数组
- **Then** 400 `NO_SELECTION`,不计票。

#### Scenario: VT-05 一次请求内重复选项被拒
- **If** `optionIds` 含重复 id(如 `["a","a"]`)
- **Then** 400 `DUPLICATE_OPTION_ID`,不计票(不出现某项 +2 而 totalVoters 只 +1)。

#### Scenario: VT-06 投给不存在的选项被拒
- **If** `optionIds` 含该 poll 不存在的 option id
- **Then** 400 `OPTION_NOT_FOUND`,不计票。

#### Scenario: VT-07 投给不存在的投票被拒
- **If** vote 的 poll id 不存在
- **Then** 404 `POLL_NOT_FOUND`。

#### Scenario: VT-08 软拦截:投过再打开只见结果
- **If** 同一浏览器成功投票(2xx)后再打开分享页
- **Then** 页面据 localStorage(键按 poll id 隔离)直接渲染结果视图,不显示投票表单。

#### Scenario: VT-09 投票失败不置已投标记
- **If** 一次投票返回非 2xx(如 `POLL_CLOSED`)
- **Then** 浏览器不写入该 poll 的已投标记,用户可重试。

## Requirement: 结果展示(Results)

#### Scenario: RS-01 百分比整数四舍五入
- **If** 某选项 `votes/totalVoters*100` = 33.33…
- **Then** 结果显示为四舍五入整数(`33%`)。

#### Scenario: RS-02 零投票显示 0%
- **If** `totalVoters == 0`
- **Then** 所有选项显示 `0%`(不出现除零错误)。

#### Scenario: RS-03 多选百分比可合计超 100%
- **If** multi poll 中多数人各选多项
- **Then** 各选项百分比按 `votes/totalVoters` 计,合计允许 > 100%。

## Requirement: 生命周期与管理(Lifecycle & Admin)

#### Scenario: CL-01 手动关闭后拒新票
- **If** 持合法 admin token `POST /api/polls/<id>/close`,随后经分享链接投票
- **Then** close 返回 2xx 且 `status="closed"`;其后 vote 返回 409 `POLL_CLOSED`;结果仍可 `GET`。

#### Scenario: CL-02 到点自动关闭拒新票
- **If** poll 设了 deadline 且当前时间 ≥ deadline,此时投票
- **Then** 409 `POLL_CLOSED`,不计票。

#### Scenario: CL-03 无 token 关闭被拒
- **If** `close` 请求不带 admin token
- **Then** 403 `INVALID_ADMIN_TOKEN`,状态不变。

#### Scenario: CL-04 错误 token 关闭被拒
- **If** `close` 带错误 admin token
- **Then** 403 `INVALID_ADMIN_TOKEN`(常量时间比较),状态不变。

#### Scenario: CL-05 重复关闭幂等
- **If** 对已 closed 的 poll 用合法 token 再次 close
- **Then** 幂等返回 2xx,`status` 仍为 `closed`。

#### Scenario: CL-06 deadline 过期持久化 closed
- **If** deadline 已过的 poll 首次被读取/写入
- **Then** 其磁盘 JSON 的 `status` 被持久化为 `"closed"`。

## Requirement: 安全(Security)

#### Scenario: SEC-01 admin token 不泄露给投票人
- **If** 请求 `shareUrl`、投票页 HTML、以及公开结果接口 `GET /api/polls/<id>`
- **Then** 响应体与页面均不包含该 poll 的 `adminToken`(全文搜索无匹配)。

#### Scenario: SEC-02 标题/选项 HTML 被转义
- **If** 标题或选项文本含 `<script>alert(1)</script>` 之类 HTML
- **Then** 在投票页/结果页/管理页均以文本形式转义呈现,不作为 HTML 执行(输出中无未转义的 `<script>`)。

## Requirement: 并发与持久化保证(Concurrency & Durability)

#### Scenario: CC-01 并发投票不丢票
- **If** 约 50 个合法投票请求并发打到同一 poll
- **Then** 落盘后 `totalVoters` = 返回 2xx 的请求数,各选项票数之和与之一致,无丢失/覆盖(对抗性并发测试)。

#### Scenario: CC-02 崩溃持久化:ack 后进程被杀数据仍在
- **If** 一次投票返回 2xx 成功后立即 `SIGKILL` 服务进程,再重启读取该 poll
- **Then** 该票仍在磁盘 JSON 中(成功=已持久化;实现须对临时文件与其父目录都 fsync 后再 rename)。

#### Scenario: CC-03 close 与 vote 并发被串行化
- **If** 一个 close 与多个 vote 并发到达同一 poll
- **Then** 二者进入同一 per-poll 队列按序执行;close 持久化后其后到达的 vote 一律 409 `POLL_CLOSED`;最终 `totalVoters` = close 生效前的成功 vote 数,无竞态丢失或越权计票。

#### Scenario: CC-04 持久化失败不谎报成功
- **If** 注入落盘失败(临时文件写/rename 失败)
- **Then** 投票返回 500 `PERSIST_FAILED`,该 poll 计数不增加,旧 JSON 文件仍可解析(未被破坏)。

# 需求:quick-poll —— 快速匿名投票小工具

> change: `quick-poll` · tier: medium · track: harden
> target lineage: **master (mainline)** —— 全新仓库,无合并禁忌
> 状态:**req-final**(STEP0 于 round 3 通过 —— VERDICT: no major issues;REQ-1..REQ-11 全部 verified)

## 1. 目标(Goal / 目标态 B)

任何人都能在几十秒内创建一个**单问题投票**(标题 + 若干选项),拿到一条分享链接;几十位同事/朋友点开链接,**匿名、免登录、无需安装**,投一票后立刻看到实时汇总结果。发起人另持一条私密**管理链接**,可随时手动关闭投票,或预设截止时间到点自动关闭。

用途:开会或群里**征集意见**。核心价值 = 发起与参与都几乎零成本。

技术路线(brainstorm 拍板,方案 1):**Node 标准库 HTTP 服务 + 每个投票一个 JSON 文件**;前端为服务端渲染的简单页面 + 少量原生 JS;不使用数据库;并发写入由应用层解决(每投票串行化 + 原子落盘)。

## 2. 目标用户

- **发起人**:开会主持人、群主、任何想快速收集意见的人。免登录;创建投票后凭"管理链接"行使管理权。
- **投票人**:同事、朋友,数量级为**几十人(设计目标约 50 人并发)**。匿名、免登录、手机或电脑浏览器点开即用。

## 3. 核心场景

1. **创建投票**:发起人填标题 + 2–10 个选项,选择单选/多选(默认单选),可选设置截止时间,提交后得到两条链接:**分享链接**(投票用)与**管理链接**(私密,含管理凭证)。
2. **投票**:投票人打开分享链接,看到标题与选项;单选投票选一项,多选投票选一或多项;提交后立刻看到实时结果(每项票数 + 百分比 + 条形,顶部显示总投票人数)。
3. **看结果**:投过的人(同一浏览器)再次打开分享链接,直接看到结果页,不再显示投票表单(软拦截)。任何人打开已关闭投票的分享链接,看到结果且不能再投。
4. **关闭投票**:发起人打开管理链接可手动关闭;若设了截止时间,到点自动关闭。关闭后拒绝新票,结果仍可查看。

## 4. UI 形态(brainstorm 草图,详细设计在 STEP2)

- **创建页**:标题输入框、选项列表(可增删,2–10 项)、单选/多选开关、可选截止时间、"生成投票链接"按钮 → 结果展示两条链接。
- **投票页**(分享链接):标题 + 选项(单选=radio,多选=checkbox)+ 提交按钮;已关闭则不显示提交。
- **结果页**:每项条形 + 票数 + 百分比 + 总人数;顶部标明投票是否已关闭。
- **管理页**(管理链接):投票概览 + "关闭投票"按钮 + 结果视图。

## 5. 数据与内容

每个投票持久化为一个 JSON 文件(文件名 = `<pollId>.json`),字段至少含:

- `id`:poll id,服务端用 CSPRNG 生成,字符集 `[A-Za-z0-9_-]`(URL-safe,≥16 字符),避免路径穿越。
- `title`:标题(trim 后非空,≤100 字)。
- `options`:选项数组,每项 `{ id, text, votes }`;`text` trim 后非空、≤50 字;选项数 2–10;**允许重复选项文本**(不去重,由发起人负责)。
- `mode`:`"single"` | `"multi"`(默认 `single`)。
- `createdAt`:创建时间(epoch millis, UTC)。
- `deadline`:可选,epoch millis(UTC);缺省表示无自动截止。
- `status`:`"open"` | `"closed"`(手动关闭时持久化为 `closed`)。
- `totalVoters`:总投票人数(= 成功投票请求数)。
- `adminToken`:管理凭证,**仅存服务端此文件**,绝不出现在分享链接/分享页 HTML/JS/接口响应中。

约束:标题 ≤100、选项 ≤50,长度口径统一为 **Unicode code points**(`[...str].length`,trim 后计;避免 emoji/代理对在边界测试中不一致);空白经 trim 判空。投票文件**长期保留**,不做自动清理;关闭后结果仍可查看。手动关闭时 `status` 持久化为 `"closed"`;因 deadline 过期而"视为 closed"的投票,首次被访问/写入时**也持久化** `status:"closed"`(便于文件状态观察,REQ-ADV-2)。

**软拦截"已投过"状态**:记在投票人浏览器 `localStorage`,键按 **poll id 隔离**(如 `voted:<pollId>`);**仅在服务端返回投票成功(2xx)后**写入;写入失败不影响服务端计票,但页面仍显示结果页;投票失败(非 2xx)**不得**写标记。不同投票之间互不污染。

## 6. deadline 语义(REQ-1)

- 输入格式:ISO 8601(前端 `datetime-local` 采集,提交给服务端换算为 epoch millis UTC 存储)。
- 判定:请求到达时若 `now >= deadline`(含刚好相等)→ 该投票视为 **closed**,拒绝新票。
- 创建时:`deadline` 必须晚于当前时间;**提交过去或等于当前的 deadline → 拒绝创建**(错误码 `DEADLINE_IN_PAST`)。

## 7. 管理凭证安全(REQ-2)

- `adminToken` 用 CSPRNG 生成,**≥128-bit** 熵(如 32 hex / 24 字节 base64url)。
- 仅存于服务端 poll JSON;校验用**常量时间比较**。
- 缺失或错误 token 的管理操作 → `403 INVALID_ADMIN_TOKEN`,不改变投票状态。
- 分享链接、投票页 HTML/JS、以及任何面向投票人的接口响应**均不得包含** `adminToken`。

## 8. 持久化与失败回滚(REQ-3)

- 一次投票**只有在持久化成功后才返回 2xx 成功**。
- 原子落盘 = 写临时文件 → `fsync(临时文件)` → `rename` 覆盖 → `fsync(目录)`;任一环节失败 → 返回 `500 PERSIST_FAILED`,**不更新任何可观测结果**(内存计数在持久化成功后才对外可见,失败即回滚/不提交)。
- 旧 JSON 文件在写入失败时必须保持可读(rename 前不破坏旧文件)。
- 启动时读到损坏/无法解析的 JSON 文件 → 记日志并跳过该文件,不导致进程崩溃。

## 9. 并发、串行化与"成功请求"定义(REQ-4 / REQ-11)

- **成功请求 = 服务端返回 2xx 的投票请求**。AC-11 的"成功请求数"以此为准。
- **每个 poll 一条 per-poll mutation queue**:所有会修改该 poll 文件的操作——**投票(vote)与关闭(close)一律进入同一队列**——按入队顺序串行执行,互不覆盖(REQ-11)。
- vote 在**执行时(而非入队时)重新检查** `status`/`deadline`:若此刻已 closed 或已过 deadline → `409 POLL_CLOSED`,不计票。
- close 成功持久化后,队列中其后的 vote 必检查到 closed 并返回 `409`。
- 计票只在持久化成功后对外可见;若持久化失败则该请求返回非 2xx 且不计票。
- MVP 规模(数十人)不设人为队列上限;请求体设**大小上限 16 KiB(16384 字节)**防滥用,超限 → `413 PAYLOAD_TOO_LARGE`。
- **重复关闭**:对已 closed 的 poll 再次 close(合法 token)→ **幂等返回 2xx**(状态已是 closed,不视为错误,REQ-ADV-2)。

## 10. 结果展示与百分比(REQ-6)

- 百分比公式:`round(optionVotes / totalVoters * 100)`,显示为**整数(四舍五入)**。
- `totalVoters == 0` 时,所有选项显示 `0%`。

## 12. 接口草案(最小,详细在 STEP2 design)

- `POST /api/polls` → 创建;body `{title, options[], mode, deadline?}`;返回 `{shareUrl, adminUrl}`。
- `GET /poll/<id>` → 投票/结果页(HTML)。
- `POST /api/polls/<id>/vote` → 投票;body `{optionIds[]}`;返回结果 JSON。
- `GET /api/polls/<id>` → 结果 JSON(**不含 adminToken**)。
- `POST /api/polls/<id>/close` → 关闭;需带 `adminToken`(header 或 body)。
- `GET /admin/<id>?token=<adminToken>` → 管理页(HTML)。

### 12.1 请求体 schema 与解析规则(REQ-9)

所有 `POST` 接口:`Content-Type: application/json`,body 上限 **16 KiB**(超限 `413 PAYLOAD_TOO_LARGE`);body 非合法 JSON → `400 INVALID_JSON`。

- `POST /api/polls`:`title` 必须为非空(trim 后)string;`options` 必须为长度 2–10 的 string 数组,每项 trim 后非空;`mode` 缺省 `"single"`,取值仅 `"single"`/`"multi"`,否则 `400 INVALID_MODE`;`deadline` 可选,必须为可解析的 ISO 8601 string,否则 `400 INVALID_DEADLINE`,且须为未来时间(否则 `400 DEADLINE_IN_PAST`)。字段缺失或类型不符 → `400 INVALID_PAYLOAD`。
- `POST /api/polls/<id>/vote`:`optionIds` 必须为**非空 string 数组**;空数组 → `400 NO_SELECTION`;含不存在的选项 id → `400 OPTION_NOT_FOUND`;数组内重复 id → `400 DUPLICATE_OPTION_ID`;single 模式长度 >1 → `400 SINGLE_CHOICE_VIOLATION`;类型不符 → `400 INVALID_PAYLOAD`。
- `POST /api/polls/<id>/close`:`adminToken` 经 body 或 header 提供;缺失/错误 → `403 INVALID_ADMIN_TOKEN`。

## 13. 可测收尾标准(Acceptance —— 每条 "if … then …" 可测)

- **AC-1 创建**:提交合法标题 + 2–10 选项 → 返回 shareUrl 与 adminUrl,投票初始 open、计票全 0。
- **AC-2 选项数下界**:少于 2 个选项 → `400 OPTION_COUNT_OUT_OF_RANGE`,不创建。
- **AC-3 选项数上界**:恰好 10 个选项 → 创建成功;多于 10 个 → `400 OPTION_COUNT_OUT_OF_RANGE`。
- **AC-4 单选投票**:single 选一项 → 该项 +1、totalVoters +1,返回结果。
- **AC-5 单选拒多**:single 提交多于一项 → `400 SINGLE_CHOICE_VIOLATION`,不计票。
- **AC-6 多选投票**:multi 选多项 → 所选各项各 +1、totalVoters +1(百分比按人数,允许合计 >100%)。
- **AC-7 软拦截**:同一浏览器成功投票后再打开分享链接 → 直接显示结果页,不显示投票表单;失败投票不置标记。
- **AC-8 手动关闭**:经管理链接(合法 token)关闭 → status 转 closed;此后投票 → `409 POLL_CLOSED`,结果仍可查看。
- **AC-9 到点自动关闭**:设了 deadline 且 `now >= deadline` → 投票视为 closed,新票 `409 POLL_CLOSED`。
- **AC-10 管理凭证隔离**:分享链接/投票页/面向投票人的接口响应均不含 adminToken;无 token 或错 token 关闭 → `403 INVALID_ADMIN_TOKEN`;仅持管理链接者能关闭。
- **AC-11 并发不丢票**:约 50 个并发投票请求(全部合法)打到同一投票 → 最终 totalVoters = 返回 2xx 的请求数,各项计票之和一致,无丢失/覆盖(**对抗性并发测试**:并行发起、校验持久化后计数)。
- **AC-12 非法输入**:空标题、空选项、超长标题/选项、不存在的选项 id、不存在的投票 → 均按 §11 错误码表拒绝,且**不写坏数据文件**(旧文件仍可解析)。
- **AC-13 XSS 防护**:标题/选项含 HTML(如 `<script>`)→ 在投票页/结果页/管理页均被转义为文本呈现,不被作为 HTML 执行。
- **AC-14 deadline 拒过去**:创建时 deadline 为过去或等于当前 → `400 DEADLINE_IN_PAST`。
- **AC-15 持久化失败不谎报成功**:注入落盘失败 → 投票返回 `500 PERSIST_FAILED`,计数不增加、旧文件不被破坏(**对抗性注入测试**)。
- **AC-16 payload 解析边界**(REQ-9):malformed JSON → `400 INVALID_JSON`;`mode` 非法 → `400 INVALID_MODE`;`deadline` 不可解析 → `400 INVALID_DEADLINE`;字段缺失/类型错误 → `400 INVALID_PAYLOAD`;body >16 KiB → `413 PAYLOAD_TOO_LARGE`。均不写坏数据。
- **AC-17 重复 optionId**(REQ-10):一次 vote 的 `optionIds` 含重复 id → `400 DUPLICATE_OPTION_ID`,不计票(不出现某项 +2 而 totalVoters 只 +1)。
- **AC-18 close/vote 并发串行**(REQ-11):close 与多个 vote 并发到达同一 poll → 二者进同一 per-poll 队列;close 持久化后其后到达的 vote 一律 `409 POLL_CLOSED`;最终 totalVoters = close 生效前成功 vote 数,无因竞态丢失或越权计票(**对抗性并发测试**)。
- **AC-19 重复关闭幂等**:对已 closed 的 poll 用合法 token 再次 close → 幂等 2xx,状态仍 closed。

# Proposal — quick-poll

## WHY(为什么做)

开会或群里需要快速征集意见,现有做法(口头举手、聊天刷屏)难汇总、易漏统计。需要一个**发起与参与都近乎零成本**的匿名投票工具:建一个投票(标题+选项)、发一条链接、几十人点开即投、投完即看结果。

## WHAT(做什么)

一个单进程 Node 标准库 HTTP 服务(方案 1,无数据库、无框架),每个投票持久化为一个 JSON 文件:

- **创建**:标题 + 2–10 选项 + 单/多选(默认单选)+ 可选截止时间 → 返回分享链接 + 私密管理链接。
- **投票**:匿名、免登录;single/multi;投完即看实时结果(票数/百分比/条形/总人数)。
- **软拦截**:同一浏览器 localStorage 记"已投",再打开直接看结果。
- **生命周期**:发起人凭管理链接手动关闭;设了 deadline 则到点自动关闭;关闭后拒新票、结果可看。
- **健壮性**:完整错误码体系、XSS 转义、per-poll 串行写队列(vote+close)、原子落盘(fsync file+dir)、并发不丢票、持久化失败不谎报成功。

规格见 `specs/`;架构见 `design.md`;实现顺序见 `tasks.md`。验收锚点:`specs/` 中 24 个 scenario ID(覆盖 req-final 的 AC-1..AC-19),含 3 项对抗性测试(并发投票 CC-01、崩溃持久化 CC-02、close/vote 并发 CC-03)。

## OUT OF SCOPE(明确不做)

- 账号/登录/用户体系(需求即匿名免登录)。
- 硬防刷(IP/实名/验证码)——已接受软拦截,防不住无痕/清缓存的硬刷。
- 现场大屏实时跳动 / 二维码现场秀(方向 A,非本工具)。
- 投票创建后编辑标题/选项;多问题问卷/分支逻辑。
- 数据库;投票文件自动清理/配额;人为并发队列上限/限流(仅设 16 KiB body 上限)。
- WebSocket/SSE 实时推送:结果"投完即看"= 提交后返回当前快照 + 可手动刷新;不做服务器主动推送(YAGNI,数十人规模)。

# Design — quick-poll

## 架构总览

单进程 Node 标准库 HTTP 服务,分层:

```
                 ┌────────────────────────────────────────────┐
   HTTP 请求 ──▶ │ server.js  路由/方法分发/16KiB body 读取     │
                 └───────┬───────────────────────┬─────────────┘
             /api/*      │                       │  /poll /admin /
          (JSON API)     ▼                       ▼   (SSR HTML)
                 ┌──────────────┐        ┌────────────────┐
                 │ validate.js  │        │  render.js     │  (HTML 转义)
                 │ payload 校验  │        │  三张页面 SSR   │
                 └──────┬───────┘        └────────────────┘
                        ▼
                 ┌──────────────┐   per-poll 串行   ┌──────────────┐
                 │  store.js    │◀── mutation queue │  queue.js     │
                 │ 领域+持久化   │                   │ Map<id,Promise>│
                 └──────┬───────┘                   └──────────────┘
                        ▼  原子落盘 (tmp→fsync→rename→fsync dir)
                 data/polls/<id>.json
```

模块职责:
- **server.js**:`http.createServer`;路由表(§12 六端点);读取 body 时强制 16 KiB 上限(超限直接 413,不缓冲全部);根据路径分派到 API handler 或 SSR。
- **validate.js**:纯函数;创建/投票 payload 的类型与范围校验;返回 `{ok, code}`。错误码集中此处,单一事实源。
- **model.js**:poll 领域对象;`create()`(生成 id/adminToken)、`applyVote()`、`close()`、`isExpired(now)`、`toPublic()`(剥离 adminToken)、`toResult()`(票数/百分比,整数四舍五入,0 人 0%)。
- **store.js**:文件读写;`load(id)`、`save(poll)`(原子落盘);启动扫描;所有写经 queue.js 串行。
- **queue.js**:`runExclusive(pollId, fn)` —— 以 `Map<pollId, Promise>` 尾接链保证同一 poll 的 mutation(vote/close)串行。
- **render.js**:创建页/投票页/结果页/管理页 SSR;所有用户文本经 `escapeHtml`;绝不注入 adminToken。
- 前端:投票页内联少量原生 JS —— 提交 fetch、成功后写 `localStorage["voted:"+pollId]`、据该键切换表单/结果视图。

## 数据模型(`data/polls/<id>.json`)

```json
{
  "id": "Ab3xY7_qP0-KmN12",
  "title": "午饭吃啥",
  "options": [{"id":"o1","text":"火锅","votes":0}, {"id":"o2","text":"麻辣烫","votes":0}],
  "mode": "single",
  "createdAt": 1751931600000,
  "deadline": null,
  "status": "open",
  "totalVoters": 0,
  "adminToken": "<32 hex chars = 128-bit CSPRNG>"
}
```
- `id`:`crypto.randomBytes(12)` → base64url(16 字符,`[A-Za-z0-9_-]`),即文件名;拒绝任何含 `/`、`.` 的 id 查找(防路径穿越)。
- `adminToken`:`crypto.randomBytes(16).toString("hex")`(128-bit);校验用 `crypto.timingSafeEqual`。

## 外部共享状态 —— 三个时刻

### 共享状态 1:磁盘 JSON 文件(`data/polls/`)
- **init(初始化)**:进程启动时确保 `data/polls/` 存在(`mkdir -p`);不预加载全部文件(按需 `load`)。创建投票时首次写入该 poll 文件。
- **runtime update(运行时更新)**:每次 vote/close 经 per-poll 队列串行:`load → 校验/改内存 → 原子落盘`。原子落盘 = 写 `<id>.json.tmp.<rand>` → `fsync(tmpFd)` → `rename` 覆盖 → `fsync(dirFd)`;任一步失败抛错 → 该请求 500,内存改动丢弃(不对外可见)。
- **cleanup / invalidation(清理/失效)**:无自动清理(long-lived,YAGNI)。失效即"逻辑关闭":`status="closed"` 或 `now≥deadline`;deadline 过期在首次 load 时 lazy 持久化为 closed(CL-06)。启动读到损坏 JSON → 记日志跳过,不崩溃。

### 共享状态 2:进程内 per-poll 队列(`queue.js` 的 `Map<pollId, Promise>`)
- **init**:模块级空 `Map`。
- **runtime update**:`runExclusive(id, fn)` 读取当前尾 Promise,追加 `.then(fn)`,写回新尾;保证同一 id 的 fn 串行,不同 id 并行。vote 与 close 共用同一 map,故二者互斥(CC-03)。
- **cleanup / invalidation**:链尾 settle 后从 map 删除已完成条目(避免无限增长);进程重启即全清(队列是易失的,真值在磁盘)。

> 单进程模型下磁盘文件的唯一写者是本进程,进程内队列即足以串行化;不引入跨进程锁(非目标)。若未来多进程部署 → 升级为文件锁/外部锁,记为 KB Decision。

## 关键正确性论证

- **不丢票(CC-01)**:所有计票写经 `runExclusive` 串行 + 每次 `load` 拿最新磁盘态 → 无读改写竞态。
- **崩溃持久化(CC-02)**:2xx 仅在 `rename` 且 `fsync(dir)` 成功后返回;fsync 覆盖文件与父目录 → 崩溃后 rename 已落盘。经典陷阱:只 fsync 临时文件不 fsync 目录会在崩溃后丢失 rename —— 本设计两者都 fsync。
- **close/vote 竞态(CC-03)**:同队列串行;vote 在 fn 执行时(而非入队时)重查 `status`/`deadline`,故 close 先执行则其后 vote 必见 closed。
- **持久化失败不谎报(CC-04)**:落盘在"改内存值 → 落盘 → 落盘成功才把结果作为响应"顺序;失败路径抛错、响应 500、下次 load 仍读旧文件。

## 测试策略(STEP5)

- 单元/集成:`node --test`,测试名带 scenario ID(TAP → `apriori verify` 绑定)。API 层用 `http` 请求真实 server 实例。
- 对抗性:
  - CC-01:`Promise.all` 并发 50 个 vote,断言最终 totalVoters=50 且各项和=50。
  - CC-02:`child_process` 起 server 子进程,vote 成功后 `SIGKILL`,重启读文件断言票在。
  - CC-03:并发 close + N vote,断言 close 后 vote 全 409、计数一致。
  - CC-04:注入 `fs` 写失败(monkeypatch/依赖注入 writer),断言 500 且文件未坏。
- E2E(Playwright,叠在绑定门之上):创建→投票→看结果核心流;并**驱动 spec 边界**——真的建到 10 选项上限、真的触发 single 拒多选,验证前端不会悄悄挡住后端 spec 的路径(P7 要求)。
- 安全:SEC-01 全文搜索响应无 token;SEC-02 断言输出转义。

## 1. Scenario coverage vs AC-1..AC-19

### SPEC-1 — `Content-Type: application/json` 缺少可测试行为
- **Description**: req-final §12.1 要求所有 `POST` 接口使用 `Content-Type: application/json`，spec 顶部也写了该约束，但没有 scenario 定义缺失/错误 Content-Type 时的 HTTP 状态和错误码；design 只设计了 16 KiB body 读取和 JSON 解析，没有明确校验 Content-Type。
- **Risk**: AC-16 的 payload 边界无法完整绑定测试；实现可能接受 `text/plain`/空 Content-Type 的 JSON，或不同 handler 行为不一致，后续需要返工统一 API 输入契约。
- **Suggestion**: 增加 scenario，例如 `PC-16 / VT-10 / CL-07 unsupported Content-Type rejected`，或统一一个跨 POST scenario；明确错误码，如 `INVALID_CONTENT_TYPE` 或并入 `INVALID_PAYLOAD`，并在 `server.js` 设计中声明所有 POST 先校验 Content-Type。

### SPEC-2 — close 的 admin token 传输方式未绑定，CL-01/CL-03/CL-04 测试不稳定
- **Description**: req-final §12.1 允许 close 的 `adminToken` 经 body 或 header 提供，但 spec 的 CL-01/CL-03/CL-04 只写“持合法 token / 不带 token / 错误 token”，没有声明测试应放在 header、body，还是两者都必须支持；design 的“未决”只确定管理页 URL query token，没有确定 `POST /api/polls/<id>/close` 的 token contract。
- **Risk**: 管理关闭是 AC-8/AC-10/AC-19 的核心路径。生产实现和验收测试可能选不同位置，导致不必要返工；若前端管理页和 API handler 约定不一致，会直接无法关闭投票。
- **Suggestion**: 在 spec/design 中固定 close API token 规则：推荐 body `{adminToken}` 和 header `X-Admin-Token` 至少一种为必选；如果两者都支持，也要写明优先级和缺失/错误 token 的判定。

### SPEC-3 — 已关闭/过期投票的分享页行为未被 scenario 明确覆盖
- **Description**: req-final 核心场景要求“任何人打开已关闭投票的分享链接，看到结果且不能再投”。spec 的 CL-01 只覆盖 close 后 vote 返回 `409` 以及结果可 `GET`；CL-02 只覆盖 deadline 到点后 vote 返回 `409`。没有 scenario 绑定 `/poll/<id>` 在 `status=closed` 或 `now>=deadline` 时必须隐藏投票表单并渲染结果视图。
- **Risk**: 实现可能只在 API 层拒票，HTML 仍显示可提交表单，造成用户体验和验收返工；deadline 自动关闭也可能只在 vote 路径触发，页面状态与服务端状态不一致。
- **Suggestion**: 增加 HTML 场景，例如 `CL-07 closed share page renders result only` 和 `CL-08 expired share page renders result only`，明确不显示提交控件。

## 2. External shared state: init / runtime update / cleanup-invalidation

### SPEC-4 — deadline lazy-close 的“读时写入”未明确进入 per-poll queue
- **Description**: design 要求 CL-06 在首次 `load` 时把过期 poll 持久化为 `closed`，同时又说每次 vote/close 经 queue 串行。问题是 GET 结果页、分享页、管理页也会触发“读取”，且 CL-06 要求读取也可能写盘；设计没有声明这些读时写入必须进入同一 per-poll mutation queue。
- **Risk**: 若 GET 在队列外 lazy-save `closed`，可与正在执行的 vote/close 并发写同一 JSON，破坏 CC-01/CC-03 的单写者假设，造成丢票、覆盖 close、或读到旧状态后写回旧计数。
- **Suggestion**: 明确任何会导致持久化的 load，包括 deadline lazy-close，必须通过 `runExclusive(pollId, fn)` 执行。纯读可以不入队，但一旦发现需要状态转移，需重新进入队列并重新 load/recheck/save。

### SPEC-5 — Promise queue 的 rejection 和 cleanup 语义不足，可能破坏 CC-03/CC-04
- **Description**: design 写的是读取当前尾 Promise 后追加 `.then(fn)` 并在 settle 后删除 Map。若某次 `fn` 因 `PERSIST_FAILED` reject，后续用 `.then(fn)` 接在 rejected tail 上的任务会被跳过，队列被“毒化”；若 settle cleanup 无条件 `delete`，也可能删除已经被后续请求替换的新 tail。
- **Risk**: CC-04 注入一次持久化失败后，同 poll 后续 vote/close 可能不再执行或错误返回；CC-03 的 close/vote 串行保证也可能被 cleanup race 打破。这会造成生产事故级的投票不可用或计数错误。
- **Suggestion**: 设计中明确 queue 模式：`const run = prev.catch(() => undefined).then(fn)`；返回 `run` 给当前请求；`tail = run.catch(() => undefined).finally(() => { if (map.get(id) === tail) map.delete(id) })`。后续任务必须在前序失败后继续执行，但当前请求仍保留自身错误响应。

- 绿色场地，无 current-state 冲突可比对。
- 设计整体符合 Node 标准库 + 单 JSON 文件 + 单进程队列的需求方向。

## 4. Spec/design mismatch or missing design

### SPEC-6 — SEC-02 只设计了 SSR escape，未覆盖投票成功后的客户端结果渲染
- **Description**: spec 要求标题/选项在投票页、结果页、管理页都以文本形式转义呈现。design 只写 `render.js` SSR 使用 `escapeHtml`，但前端 JS 会 fetch 投票并切换表单/结果视图；若该结果视图用 API JSON 动态渲染选项文本，设计没有要求使用 `textContent` 或客户端 escape。
- **Risk**: 含 `<script>` 的标题/选项可能在投票成功后的动态结果视图被 `innerHTML` 注入，绕过 SSR escape，形成 XSS。安全问题不能作为 advisory。
- **Suggestion**: 在 design 的前端部分明确：所有来自 poll JSON/API 的 title/option text 在客户端 DOM 更新时只能用 `textContent`/属性安全赋值，禁止拼接进 `innerHTML`；SEC-02 测试需覆盖初始 SSR 和投票后动态结果视图。

## 5. Security / durability / concurrency scrutiny

- `id` 字符集和拒绝 `/`、`.` 的 path traversal 防线方向正确，但实现时还需在 URL decode 后校验。
- CC-02 的 atomic-write 顺序 `tmp -> fsync file -> rename -> fsync dir` 能支撑“2xx 后崩溃仍持久化”的设计目标，前提是 2xx 严格晚于目录 fsync 成功。
