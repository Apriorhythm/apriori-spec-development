## Current state A (confirmed by direct code read, not just KB)

- `server.js` is a hand-rolled router over `http.createServer`; no cookie parsing/writing exists anywhere (no `Cookie` header read, no `Set-Cookie` write) — confirms KB.
- `lib/polls.js`: `vote(id, choices)` has no identity parameter; `getPoll(id)` returns `store.get(id)`, which is the **live object reference stored inside the store's in-memory map**, not a copy. `view(poll)` takes no identity parameter.
- `lib/store.js`: `put(poll)` does exactly two statements in order — `data[poll.id] = poll;` then `save();`. Because `poll` handed to `vote()`'s `store.put(poll)` call is normally the **same object** already sitting at `data[poll.id]` (fetched via `getPoll`→`store.get`), the `data[poll.id] = poll` line is a no-op reassignment — the in-memory map was already mutated the instant `poll.votes.push(choices)` ran, **before `store.put` is even called**. `save()` writing to disk is the only step that can fail (`fs.writeFileSync`/`fs.renameSync` throwing, e.g. disk full or an injected fault for a test).
- `public/poll.html`: `voted` state today is 100% localStorage-driven (`votedKey`); the vote button's fetch relies on the browser's default same-origin cookie behavior (fetch's default `credentials: 'same-origin'` already sends cookies for same-origin requests — no client code change needed there for cookies to ride along).
- Tests: `npm test` runs `store.test.js`, `polls.test.js`, `server.test.js` (node:test, all sync/scratch-dir based, no injected I/O failures today). `test:e2e.test.js` is a separate Playwright target, not part of default `npm test`.

## Target state B

Per `requirement/req-final.md` B1–B8 / AC1–AC11: cookie-carried anonymous voter identity, HMAC-signed, issued only from `GET /api/polls/:id` and successful `POST .../vote`; server-side one-vote-per-identity-per-poll enforcement that is atomic under concurrency and all-or-nothing under persistence failure; `voted` in the public view contract; `voters` digest field alongside the untouched `votes` array; explicit cookie/key lifecycle.

## Gaps and risks (A → B)

1. **HIGH — store.put's mutate-then-save ordering breaks the AC9 all-or-nothing guarantee as currently structured.** Since the poll object mutated by `vote()` is the *same reference* already live in the store's map, a failing `save()` still leaves the in-memory map holding the pushed vote / voter digest — there is no natural rollback point. Implementing B4's "failure → memory unchanged" literally requires **either**: (a) restructuring `store.put` to only swap the in-memory reference in on a *successful* `save()` (write-then-commit ordering), or (b) having `polls.vote()` operate on a **cloned** poll object and only call a store method that installs the clone after a successful disk write, catching failure and leaving the original untouched. This is a design decision for STEP2, not an implementation detail — flagging it now because it is the mechanism AC9 (failure-injection test) actually exercises; a naive "wrap in try/catch and hope" will not satisfy it given the current aliasing.
2. **MED — concurrency (AC8) is achievable for free only if the whole check→count→mark→persist chain stays fully synchronous.** Node's single-threaded event loop already serializes two "simultaneous" `POST .../vote` calls as long as no `await`/callback yield point is introduced between reading `poll.votes`/`poll.voters` and calling the synchronous `store.put`. Risk: it would be easy to accidentally break this by using `crypto.randomBytes` in async-callback form, an async cookie-secret read, or any Promise-based step inside the vote path — any of those reintroduces the race B4/AC8 is meant to close. STEP2's design doc must say explicitly "the vote path stays synchronous end-to-end" as a design constraint, not just an implementation detail.
3. **MED — cookie-secret file lifecycle needs its own init path, ahead of/independent from `store.save()`'s directory creation.** `store.js` only calls `fs.mkdirSync(dataDir, {recursive:true})` inside `save()`, i.e., on first poll write. The `cookie-secret` file (B2) may need to be generated on server startup / first `GET /api/polls/:id`, before any poll has ever been created (e.g., a fresh dataDir with zero polls) — the new cookie-secret module must ensure `dataDir` exists itself rather than assuming `store.js` already created it.
4. **LOW-MED — domain-layer signature changes ripple through every existing call site.** `vote(id, choices)` → `vote(id, choices, voterId)`, `getView(id)` → needs an optional voter identity to compute `voted`, `view(poll)` → `view(poll, voterId?)`. All three existing call sites in `server.js` (lines ~59, ~63) and the admin call sites (`adminView`/`close`, which must **not** pass a voter identity so `voted` never appears in admin view per B6) need updating in lockstep — a single missed call site is exactly the kind of "spec'd but not designed" gap P5/P8 would catch, so STEP2's design doc should enumerate every call site explicitly.
5. **LOW — existing test suite (`polls.test.js`, `server.test.js`) calls `polls.vote(id, choices)` and `polls.getView(id)`/`polls.create(...)` directly with the old 2-arg signature; every one of those call sites needs an explicit third argument (a fixed test voter id) or the tests silently start hitting `voterId === undefined` paths.** req-final.md's §4 already flagged the signature change but left "how tests get rewritten" to STEP2, per its own Q3 resolution — this is the concrete enumeration STEP2 needs.
6. **LOW — Playwright/E2E test seam for AC7-Browser's "delete cookie mid-session" step.** `poll.html` polls every 3s (`setInterval(load, 3000)`); the reviewer's ADV-r2-002 already flagged that a test must control timing so the 3s poll doesn't silently re-issue a fresh cookie via its own `GET /api/polls/:id` call between "delete cookie" and "click vote" — Playwright's `context.clearCookies()` + immediate click, or freezing the interval in the test, resolves it; noting it here so STEP2's tasks.md doesn't drop it.
7. **LOW — AC9 (failure-injection) test seam.** `lib/store.js` has no built-in fault-injection hook. The test needs a real adversarial condition (per RUNBOOK's guarantee-claim discipline — no mocking a "would have failed" path), e.g., constructing the store's `dataDir` such that the `.tmp` write or the rename genuinely fails (a read-only directory, or a directory replaced by a file) — STEP2 must pick a concrete, real mechanism, not a stub.

## Top risks carried forward (medium tier — folded into STEP2 rather than a separate gate)

Risks 1 and 2 above are the ones most likely to cause rework if under-designed — they directly gate whether AC8/AC9 (the two "hardest" new acceptance criteria) are actually satisfiable by a straightforward implementation. STEP2's design.md must resolve both explicitly before STEP5 starts.
