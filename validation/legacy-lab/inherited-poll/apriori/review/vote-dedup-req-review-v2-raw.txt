### Public interfaces (HTTP API — `server.js`)

Zero external dependencies (Node builtins only); JSON in/out, `charset=utf-8`; errors are
`{ error: <Chinese message> }` with the `PollError.status` code, or 500 + generic message + `console.error`
for unexpected throws.

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/` | — | `public/index.html` (create-poll page) |
| GET | `/style.css` | — | stylesheet |
| GET | `/poll/:id` | — | `public/poll.html` (id not validated against store — page loads, then fetches JSON and shows the error) |
| GET | `/admin/:token` | — | `public/admin.html` (same: token validity checked only by the JSON call the page makes) |
| POST | `/api/polls` | `{question, options[], multiple?, deadline?}` | 201 `{id, adminToken}` |
| GET | `/api/polls/:id` | — | 200 public view (see `view()` below) or 404 |
| POST | `/api/polls/:id/vote` | `{choices:[int,...]}` | 200 public view, or 400/404/409 |
| GET | `/api/admin/:token` | — | 200 view (by admin token) or 404 |
| POST | `/api/admin/:token/close` | — | 200 view (`closed:true`) or 404 |

Route matching: `id` and `token` path segments are matched by `^[a-z0-9]+$` at the router level (`server.js`);
actual existence is checked inside `lib/polls.js`. No auth/session of any kind — `adminToken` is a bearer
capability string embedded in the admin URL, nothing else gates `/api/admin/*`.

### Domain logic (`lib/polls.js`)

- `create(input)` — validates `question` (non-empty, trimmed, ≤200 chars) and `options` (trim+drop-empty,
  2..20 items, each ≤100 chars); optional `deadline` must parse and be strictly in the future (`now()` is
  injectable for tests). Generates `id` (6 chars) and `adminToken` (16 chars) from a shared 31-char alphabet
  (`abcdefghjkmnpqrstuvwxyz23456789` — visually-ambiguous chars `i l o 0 1` excluded) via `crypto.randomBytes`.
  Stores the full poll object (**including `adminToken`**) via `store.put`.
- `view(poll)` — the ONLY public projection: strips `adminToken` and the raw `votes` array, returns
  `{id, question, options, multiple, deadline, closed, open, counts, total}`. `counts[i]` = number of
  votes whose `choices` array includes index `i`; `total` = `votes.length` (i.e. number of vote *events*,
  not the sum of counts — a multi-select vote counts once toward `total` but toward multiple `counts[i]`).
- `isOpen(poll)` = `!closed && (!deadline || now() < deadline)`.
- `vote(id, choices)` — **current behavior has NO duplicate-vote defense of any kind server-side.**
  Checks (in order): poll exists (404) → not closed (409 `投票已关闭`) → not past deadline (409
  `投票已过截止时间`) → `choices` is a non-empty array (400) → every choice is an integer in
  `[0, options.length)` and choices has no duplicate indices (400 `选项不合法`) → single-select poll
  has exactly one choice (400). On success: `poll.votes.push(choices)` — **unconditionally, no caller
  identity is recorded or checked** — then persists and returns the view. Nothing in this function, the
  store, or the HTTP layer associates a vote with a browser/cookie/IP; the same `curl -X POST .../vote`
  can be replayed unboundedly and every call succeeds and increments the count (verified empirically:
  3 identical curl-equivalent POSTs against a fresh poll → 3× 200, `total` 1→2→3).
- `findByToken(token)` — **linear scan** over every stored poll (`store.all()`) comparing `adminToken`;
  fine at current scale, would need an index if poll count grows large.
- `adminView` / `close` both resolve the poll via `findByToken` — no separate rate limiting or attempt
  cap on token guessing (16 random chars from a 31-char alphabet is the only defense).

### Data model / persistence (`lib/store.js`)

- One JSON file: `<dataDir>/polls.json` — a flat object keyed by poll `id`, values are full poll records
  (including `adminToken` and raw `votes`). Loaded once into memory at `createStore()` time; every `put`
  rewrites the **entire file** (no per-poll files, no append log).
- **Three moments:**
  - *init*: `load()` reads the whole file synchronously at store construction; missing file → start
    from `{}`; JSON parse failure → the corrupt file is renamed to `<file>.bak-<timestamp>Z` and a fresh
    `{}` is used (logged via `console.error`, not surfaced to any HTTP caller).
  - *runtime update*: `put(poll)` mutates the in-memory object, then `save()` — write to `<file>.tmp`,
    `fs.renameSync` over the real file. This is an atomic rename (no torn writes, no leftover `.tmp` on
    success — asserted by `store.test.js`), but **`save()` does not call `fsync`** on the temp file or the
    containing directory, so this store makes no crash-durability guarantee across a real power loss /
    kill -9 — only "no partial/corrupt file under normal process exit". Nothing in the code or tests
    claims durability beyond that; do not read one in.
  - *cleanup/invalidation*: none — there is no TTL, no poll deletion, no vote retraction. `data/` is
    gitignored; nothing in the app itself prunes it.
- Poll record shape: `{id, adminToken, question, options[], multiple, deadline (ISO string|null),
  closed, votes: [ [choiceIndex,...], ... ], createdAt}`. `votes` entries carry **no voter identity, no
  timestamp** — just the chosen index array from that call.

# req-v2 — vote-dedup：服务端防重复投票（cookie 级别）

- change: vote-dedup
- tier: medium · track: harden

- 现状事实来源: `apriori/truth/polls.md`（已经人扫过——注意其 DEC-0：本项目没有任何存活的设计决策记录，现状描述以代码为准）
- 上一版评审: `apriori/review/vote-dedup-req-review-v1.md`（7 个正式问题，见第 5 节逐条处理）

## 1. 背景与问题（现状 A）

当前"防重复投票"只存在于前端：`poll.html` 投票成功后写 `localStorage['voted:'+id]`，仅用于隐藏表单。服务端 `vote()` 对调用者身份零感知——同一请求用 curl 原样重放，每次都 200 并计票（已实测：3 次重放 → total 1→2→3）。服务端目前没有任何 cookie 的读写代码。

## 2. 目标（目标态 B）

服务端以**匿名、不可伪造的投票者标识**（经 HttpOnly cookie 承载）为准，拒绝同一标识对同一投票的重复投票。不引入登录/账号体系。

### 行为要求（已封版，无开放问题）

- **B1 标识下发**：客户端请求 `GET /api/polls/:id` 时，若请求未带有效标识 cookie，服务端生成匿名投票者标识并经 `Set-Cookie` 下发；已带有效标识的请求不重复下发。标识全站一个（不按 poll 区分）。`POST /api/polls/:id/vote` **成功响应（200）** 时同样确保调用方带着（或已被下发过）有效标识——即成功投票必然对应一个已下发的标识,不会出现"投中了但从未 Set-Cookie"的情形；**失败响应（400/404/409）不下发新 cookie**（不奖励非法请求）。`GET /poll/:id`、`GET /admin/:token`、`GET /`、`GET /style.css` 等页面/静态路由**不下发、不读取**该 cookie——签发入口只在 API 层，页面加载后必然会调用 `GET /api/polls/:id`，行为等价，实现集中在一处。
  - cookie 名称：`pv`（poll voter，避免暴露实现细节）。
  - 属性：`HttpOnly; SameSite=Lax; Path=/`；不设 `Secure`（本项目当前无 HTTPS 部署证据，KB 未记录）；`Max-Age=31536000`（365 天）。
- **B2 标识不可伪造**：标识格式为 `<random>.<hmac-sha256 签名, base64url>`；`random` 为 `crypto.randomBytes(16)` 的 base64url 编码。签名密钥（32 字节随机）持久化于 `<dataDir>/cookie-secret`（与 `polls.json` 同目录，权限依赖操作系统默认，不额外加固——与本项目现有"零额外基础设施"风格一致）：
  - 密钥文件不存在 → 生成新密钥并写入（`fs.writeFileSync`，同步，遵循 store 现有的同步 I/O 风格）；
  - 密钥文件存在 → 读取复用；
  - 密钥文件存在但**内容不是合法长度**（读取后长度不等于预期字节数）→ 视为损坏：**服务启动失败**（抛出错误，非静默重建）——静默重建会让所有既有 cookie 静默失效且无操作留痕，優先选择显式失败，由运维介入；这与该文件已损坏时"重建更省事但吞掉一次隐性数据丢失"的取舍相反，选择更保守的一侧。
  - 校验失败（签名不匹配、格式不符）的 cookie 值，在 GET 路径按"无标识"处理（视为新访客，可能触发重新下发）；在 POST 路径按"无有效标识"处理（见 B3，拒绝）。
- **B3 投票必须携带有效标识**：`POST /api/polls/:id/vote` 无 cookie 或标识非法（格式错误/签名不匹配）→ `403` + `{error:"未获得投票标识"}`，**不计票**，**不下发新 cookie**（见 B1）。正常浏览器用户不受影响（打开页面即已通过一次 GET 领到标识）。
- **B4 同一标识同一投票只能投一次，且检查/计票/持久化对调用者是 all-or-nothing**：
  - 重复投票 → `409` + `{error:"你已经投过这个投票了"}`，票数不变。
  - 首次投票成功时，服务端在**同一次 `store.put`/文件落盘**中原子性地写入两件事：投票计入 `votes`，且该标识被记为"已投过该 poll"。**检查是否已投 → 计票 → 标记已投 → 持久化，四步必须在单个同步调用链内完成，中途不让出事件循环（不出现两个并发请求都通过检查的窗口）**——Node 单线程 + 当前代码同步文件 I/O 的组合天然满足这一点，只需保证新代码不引入 `await`/回调把这四步拆开成非原子的多个 tick。
  - 若 `store.put()`/文件写入抛错：**响应 500**，且**进程内存中的票数与去重标记必须回滚到写入前的状态**（不出现"返回失败但内存已计票"或"计票成功但去重标记丢失"）——具体做法：先在内存副本上应用变更、调用 `store.put()`成功后才真正提交内存状态；或捕获写入异常后撤销内存改动。重启后（或下一次成功请求前）不得看到这次失败请求造成的任何计票/去重痕迹。
- **B5 跨投票互不影响**：同一标识可对不同 poll 各投一票。
- **B6 前端以服务端为准 —— `voted` 字段完整契约**：
  - `GET /api/polls/:id` 的响应新增布尔字段 `voted`：请求带有效标识且该标识已投过此 poll → `true`；否则（无 cookie / 非法 cookie / 有效 cookie 但未投过）→ `false`。
  - `POST /api/polls/:id/vote` 的**成功（200）**响应同样携带 `voted: true`（刚投完，视为已投）。
  - `POST /api/polls/:id/vote` 的失败响应（400/403/404/409）**不新增 `voted` 字段**（沿用现有错误体 `{error}`）。
  - `GET /api/admin/:token`、`POST /api/admin/:token/close` 的响应（admin view）**不包含 `voted` 字段**——admin 视图无请求方标识语境，字段无意义。
  - `poll.html` 据此显示"已投过"状态（localStorage 可保留为辅助展示，但判定以服务端 `voted` 字段为准，两者冲突时以服务端为准）；服务端 4xx/409 拒绝必须以可见文案呈现给用户（`#error` 区域或等价可见元素），不得吞掉、不得静默失败。
- **B7 隐私**：标识是随机匿名值，不含且不派生任何个人信息；不记录、不使用 IP；投票内容与标识的绑定仅用于防重复判定，不在任何视图/接口中暴露"谁投了什么"——公开视图（`view()`）和 admin 视图均不返回 `votes` 原始数组、`voters`/去重标记原始值、cookie 原值或标识摘要。
- **B8 数据模型与兼容**（回应 REQ-005）：
  - poll 记录新增字段 `voters: string[]`——存储已投过该 poll 的标识的 **HMAC 摘要**（不存标识明文/签名整串，进一步降低意外泄露风险；摘要算法与 B2 签名可复用同一密钥的 HMAC，输入为标识的 `random` 部分）。
  - 既有 `votes: [[choiceIndex,...],...]` 数组**结构不变**，继续是本次改动的计票口径来源；`counts`/`total` 的计算方式不变（`counts[i]` 数投票 events 中包含选项 i 的次数，`total = votes.length`）。
  - 旧 poll（无 `voters` 字段，即本次改动前创建的记录）视为 `voters: []`（没有任何标识投过），**其历史投票不追溯关联到任何标识、不清洗、不迁移**，按原样计入 `counts`/`total`；这些旧投票不会被"去重"，因为它们本来就没有关联标识——这与第 3 节 out-of-scope 的既有声明一致，此处只是把隐含的存储形态显式化。
  - `view()`（公开）与 `adminView`（管理）都不返回 `voters` 字段本身，只在公开视图里派生出布尔 `voted`（见 B6）。

### 验收标准（全部可测，if…then）

- AC1 无 cookie 的客户端 `GET /api/polls/:id` → 应答含 `Set-Cookie: pv=...`（HttpOnly）；带该 cookie `POST …/vote` 合法选项 → 200，票数 +1，响应体含 `voted:true`。
- AC2 同一 cookie 对同一 poll 再次 `POST …/vote` → 409，`{error:"你已经投过这个投票了"}`，`total` 不变。
- AC3 含 cookie 的同一 curl 请求原样重放 3 次 → 仅第一次 200，其余两次 409，票数只 +1。
- AC4 不带 cookie 的 `POST …/vote` → 403 `{error:"未获得投票标识"}`，不计票；伪造/篡改签名的 cookie 同样 403 拒绝，不计票；两种情况响应都不含 `Set-Cookie`。
- AC5 同一 cookie 对另一个 poll 投票 → 200（跨 poll 不互相误伤），该 poll 的 `voted` 各自独立。
- AC6 投票成功后重启服务（同一数据目录）：同一 cookie 再投同一 poll → 仍 409；票数与重启前一致。**验证方式必须是重启后经应用自身的加载路径读回**（新起 server/store 实例走 API 断言），不是直接翻 JSON 文件。
- AC7-API `POST /api/polls/:id/vote` 无 cookie 直连（curl 等价）→ 403，响应体 `{error:"未获得投票标识"}`（API 层断言，非浏览器渲染）。
- AC7-Browser 浏览器端到端：a) 投完票刷新页面显示"已投过"；b) 清掉 `localStorage` 后刷新仍显示"已投过"（证明判定来自服务端 `voted` 字段而非 localStorage）；c) 页面已加载（已持有 cookie）后，删除浏览器的投票者 cookie，再点击投票按钮 → 页面 `#error`（或等价可见元素）显示拒绝文案，表单不被静默隐藏、不静默失败。
- AC8-并发 同一有效 cookie 对同一 poll **并发**发起两个合法 `POST …/vote`（Promise.all 或等价并发发起）→ 最终只有一个返回 200，另一个返回 409，`total` 只 +1。
- AC9-失败注入 对 store 注入一次写入失败（`store.put` 抛错）→ `POST …/vote` 返回 500；随后（不重启，同进程）再次 `GET /api/polls/:id` 读到的 `total`/`counts`/`voted` 与失败请求发生前完全一致（内存未残留该次失败请求的计票或去重痕迹）。
- AC10-密钥缺失/损坏 首次启动（无 `cookie-secret` 文件）→ 服务正常启动，文件被创建；把文件内容替换成非法长度内容后重启 → 服务启动失败（进程以非零退出或抛出未捕获异常，测试可通过尝试构造 store/server 实例判断）。
- AC11-既有行为不回归：建投票校验、计票口径（`counts`/`total` 语义）、关闭、截止、管理链接等现有测试语义全部保持；`view()` 继续不泄露 `adminToken` 与原始 `votes`，也不得泄露 `voters`、投票者标识与"谁投了什么"。

### 防护边界（明确接受的限制——不是本次要解决的问题）

- 清 cookie、换浏览器、隐身窗口可以再投——cookie 级别防护的固有上限，需求方已明确接受（"cookie 级别就行"）。

## 正式问题

### 维度 1：目标态 B 是否清晰无歧义

#### REQ-001 — 文档仍保留开放问题，目标态未封版

**Description:**  
第 4 节仍列出 Q1/Q2/Q3。尤其是无标识 POST 的状态码、是否在 `/poll/:id` HTML 请求下发 cookie、领域层 `polls.vote()` 签名如何变化，都会直接影响实现和测试。

**Risk:**  
不同实现者可能选择不同状态码、cookie 下发入口和内部 API 形态，导致实现虽各自合理但验收不一致。

**Suggested fix:**  
把开放问题改成明确决定。例如：无/非法标识 POST 固定返回 `403`；仅 `GET /api/polls/:id` 下发/刷新投票者 cookie；领域层接口明确为 `getView(id, voterId?)`、`vote(id, choices, voterId)` 或等价签名。

#### REQ-002 — `voted` 字段的公开视图契约不完整

**Description:**  
B6 只声明“携带已投标识的请求返回 `voted: true`”，但未说明以下情况：无 cookie、非法 cookie、有效 cookie 但未投过、投票成功响应、404 响应、管理视图是否包含 `voted`。当前代码的 `view(poll)` 是无身份上下文的公共投影视图，这一接口变化需要明确。

**Risk:**  
实现可能让 `voted` 缺省、返回 `false`、只在 GET 返回、或误加到 admin view；前端和测试会产生分歧，也可能意外扩大接口暴露面。

**Suggested fix:**  
声明公共投票视图的完整契约：`GET /api/polls/:id` 和成功 `POST /vote` 均返回布尔 `voted`；有效标识且已投为 `true`，否则为 `false`；无/非法 cookie 的 GET 视同新标识并返回 `false`；admin view 是否不包含该字段也要明确。

#### REQ-006 — Cookie 与签名密钥生命周期不够精确

**Description:**  
B1 的“长有效期”和 B2 的“签名密钥持久化在数据目录”没有定义具体可验收行为：cookie 名称、有效期下限或精确 `Max-Age/Expires`、密钥文件位置、首次生成、重启复用、密钥文件缺失/损坏时的处理。

**Risk:**  
实现可能选择一天、一年或会话级有效期；密钥重建策略不同会让已有 cookie 是否失效不可预测。密钥损坏时如果静默重建，也会造成所有既有 cookie 失效但无明确验收依据。

**Suggested fix:**  
补充固定契约。例如：cookie 名为 `poll_voter`；`Max-Age=31536000`；密钥文件为 `<dataDir>/cookie-secret`；文件不存在时生成并保存；存在时复用；读取失败返回 500 或启动失败；非法 cookie 在 GET 上按无标识处理，在 POST 上拒绝。

### 维度 2：边界与异常路径是否覆盖

#### REQ-003 — 同一 cookie 并发投票的结果未定义

**Description:**  
AC2/AC3 覆盖了串行重复提交，但没有覆盖两个相同 cookie 对同一 poll 近同时提交的行为。

**Risk:**  
如果实现把“检查是否已投”和“写入投票/标记已投”拆开且中间存在异步边界，可能两个请求都通过检查并双计票，核心防重复目标失效。

**Suggested fix:**  
增加并发验收：同一有效 cookie 对同一 poll 同时发起两个合法 `POST /vote`，则最多一个返回 200，其余返回 409，最终 `total` 只增加 1。并声明检查、计票、标记已投必须作为一个原子逻辑步骤完成。

#### REQ-004 — 持久化失败时的回滚/一致性未定义

**Description:**  
B4 要求首次投票成功时“已投过该 poll”随 poll 数据一起落盘，但未说明 `store.put()`/文件写入失败时，内存中的票数和去重标记应如何处理。当前 store 是先改内存对象再写整个 JSON 文件，失败路径尤其需要明确。

**Risk:**  
实现可能返回 500 但内存中已经计票，或计票成功但去重标记未持久化，导致重启前后行为不一致、重复投票漏拦或票数异常。

**Suggested fix:**  
声明失败语义：计票和去重标记必须对调用者表现为 all-or-nothing；持久化失败时返回 500，且活动进程内的票数与去重状态不得改变。至少增加可注入失败 store 的单测，断言失败后再次读取视图不变。

### 维度 3：隐含但未声明的状态变化/副作用

#### REQ-005 — 新旧投票数据模型兼容规则未声明

**Description:**  
当前 poll 记录是 `votes: [[choiceIndex,...]]`。需求要求新增“该标识已投过该 poll”的持久状态，并且 out of scope 声明历史旧投票无标识、保持原样计票，但没有定义新字段/新 schema 与旧 `votes` 数组如何共存。

**Risk:**  
实现可能把 `votes` 从数组改成对象数组，破坏现有 `counts`/`total` 语义、旧数据加载或 `view()` 裁剪规则；也可能把投票者标识和选择直接绑在同一结构中，增加隐私暴露风险。

**Suggested fix:**  
明确持久化形态和兼容规则。例如：旧 `votes` 数组保持有效；新增 `voters`/`votedBy` 存防重用的标识摘要；`counts` 和 `total` 继续只按 `votes` 计算；公开视图不得返回 `votes`、`voters`、cookie 原值或标识摘要；不做历史迁移但必须能读取旧 poll。

### 维度 4：验收标准是否可测试

#### REQ-007 — AC7 的“无 cookie 直连 POST 拒绝文案对用户可见”不可按字面做浏览器端到端断言

**Description:**  
AC7 把“浏览器端到端”和“无 cookie 直连 POST”放在一起，但直连 POST 没有页面承载错误文案；正常浏览器访问 `/poll/:id` 后又会先 GET 领取 cookie。

**Risk:**  
测试作者无法判断应通过 curl/API 断言 JSON 错误，还是构造浏览器页面态断言 `#error` 可见，导致验收实现不一致。

**Suggested fix:**  
拆成两个可测 AC：API 层无 cookie POST 返回指定 4xx 和 `{error}`；浏览器层在页面已加载后删除投票者 cookie，再点击投票按钮，页面 `#error` 显示该错误文案且表单不被静默隐藏。

     9	## 1. 背景与问题（现状 A）
    10	
    11	当前"防重复投票"只存在于前端：`poll.html` 投票成功后写 `localStorage['voted:'+id]`，仅用于隐藏表单。服务端 `vote()` 对调用者身份零感知——同一请求用 curl 原样重放，每次都 200 并计票（已实测：3 次重放 → total 1→2→3）。服务端目前没有任何 cookie 的读写代码。

    13	## 2. 目标（目标态 B）
    14	
    15	服务端以**匿名、不可伪造的投票者标识**（经 HttpOnly cookie 承载）为准，拒绝同一标识对同一投票的重复投票。不引入登录/账号体系。
    16	
    17	### 行为要求（已封版，无开放问题）
    18	
    19	- **B1 标识下发**：客户端请求 `GET /api/polls/:id` 时，若请求未带有效标识 cookie，服务端生成匿名投票者标识并经 `Set-Cookie` 下发；已带有效标识的请求不重复下发。标识全站一个（不按 poll 区分）。`POST /api/polls/:id/vote` **成功响应（200）** 时同样确保调用方带着（或已被下发过）有效标识——即成功投票必然对应一个已下发的标识,不会出现"投中了但从未 Set-Cookie"的情形；**失败响应（400/404/409）不下发新 cookie**（不奖励非法请求）。`GET /poll/:id`、`GET /admin/:token`、`GET /`、`GET /style.css` 等页面/静态路由**不下发、不读取**该 cookie——签发入口只在 API 层，页面加载后必然会调用 `GET /api/polls/:id`，行为等价，实现集中在一处。
    20	  - cookie 名称：`pv`（poll voter，避免暴露实现细节）。
    21	  - 属性：`HttpOnly; SameSite=Lax; Path=/`；不设 `Secure`（本项目当前无 HTTPS 部署证据，KB 未记录）；`Max-Age=31536000`（365 天）。
    22	- **B2 标识不可伪造**：标识格式为 `<random>.<hmac-sha256 签名, base64url>`；`random` 为 `crypto.randomBytes(16)` 的 base64url 编码。签名密钥（32 字节随机）持久化于 `<dataDir>/cookie-secret`（与 `polls.json` 同目录，权限依赖操作系统默认，不额外加固——与本项目现有"零额外基础设施"风格一致）：
    23	  - 密钥文件不存在 → 生成新密钥并写入（`fs.writeFileSync`，同步，遵循 store 现有的同步 I/O 风格）；
    24	  - 密钥文件存在 → 读取复用；
    25	  - 密钥文件存在但**内容不是合法长度**（读取后长度不等于预期字节数）→ 视为损坏：**服务启动失败**（抛出错误，非静默重建）——静默重建会让所有既有 cookie 静默失效且无操作留痕，優先选择显式失败，由运维介入；这与该文件已损坏时"重建更省事但吞掉一次隐性数据丢失"的取舍相反，选择更保守的一侧。
    26	  - 校验失败（签名不匹配、格式不符）的 cookie 值，在 GET 路径按"无标识"处理（视为新访客，可能触发重新下发）；在 POST 路径按"无有效标识"处理（见 B3，拒绝）。
